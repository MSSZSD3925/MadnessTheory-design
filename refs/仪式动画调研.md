# 魔法模组「仪式进行中的动画与表现」调研

目标：为我们的「唤醒仪式」找出可借鉴的实现方式。

**我们的用例（复述，后文简称"用例"）**：

1. 玩家手持书本右键一尊雕像方块
2. **粒子流**：像附魔台那样的符文/标准银河字母，**从玩家身上流出、飞向目标雕像**，持续约 3 秒
3. **物体剧烈抖动**：雕像台座上放着的物品在这 3 秒里明显抖动
4. 3 秒后一声"丁"的提示音
5. 物品变成法杖，**留在雕像的台座上**（不是给玩家）

**已核对的技术现状**：目标方块有自己的 BlockEntity，存着 `ItemStack contained`，已有
`getUpdatePacket()` + 手写的 `getUpdateTag()`；物品由 BER 渲染（`extractRenderState` / `submit` 两段式，
`SubmitNodeCollector`）。

## 0. 结论速览（先给答案）

| 问题 | 结论 |
|---|---|
| 原版 `ParticleTypes.ENCHANT` 自带朝向玩家的速度吗？ | **没有速度。它不是"飞出去"，而是"从不远处飞回来"。** 第 3~5 个参数是**位移向量**（终点−起点），粒子在存活期内从 `pos+offset` 线性插值到 `pos`。见 §1 |
| 能用 `sendParticles` 的速度参数把它引向别处吗？ | **可以，但语义是"位移"不是"速度"。** 想让它从玩家飞向雕像：**在雕像位置 spawn，offset 指向玩家**。方向、长度都要自己算。粒子寿命固定 25~30 刻，所以**长距离会飞不到**，见 §1.4 |
| 有没有"粒子沿路径飞向目标"的做法？ | 四家**全都有，而且是三种不同流派**：<br>• **插值撒点**（最省事）：Ars Nouveau `ParticleUtil.beam()` / `doParticleBeam()`、Botania `doParticleBeam()`、`SPARK_NET_INDICATOR`——按固定步长沿直线撒原版/自写粒子<br>• **自带目标的粒子类**（讲究）：Thaumcraft `FXBoreSparkle`（每刻朝目标转向 + 抖动）、Ars Nouveau `ParticleLine`（构造时吃下 dest 坐标，自己 lerp）<br>• **真实实体**：Ars Nouveau `EntityFollowProjectile`（服务端实体，朝 `BlockPos dest` 归航 + 沿轨迹撒粒子） |
| 方块上物品抖动怎么做的？ | **全都在 BER/TESR 里改 `poseStack` 的 translate/mulPose**，没有例外，也没有别的层。抖动参数见 §2.3 汇总表 |
| 持续数秒仪式的状态放哪？ | **四种都放 BlockEntity 字段**（Thaumcraft/Astral 把"配方+进度"打包成对象）。没有用 Capability 或独立 SavedData 的 |
| 怎么同步？ | **两家（Botania / AN）把"是否在仪式中"做成一个同步字段，客户端自己按 tick 算动画**；只有需要真实进度条时才同步进度值。Thaumcraft 用 `HashMap<key, SourceFX>` + 一个 20 字节的小包；Astral 每 4 刻同步一次 `serverSyncAttTick` |
| 防"半途卡死"？ | Astral 做得最完整：`ActiveCraftingTask` 有 **ACTIVE / WAITING / PAUSED** 三态状态机，`tryProcess` 返回 false 就停在那儿，NBT 全程持久化 → 断电/卸载/重启回来能续；Astral 还专门写了 `checkClientEffectIntegrity()` 处理客户端残留的镜头动画 |
| "丁"的一声 | **Botania 有现成的 `BotaniaSounds.ding`**（`ding`），用在绑定成功等处；Astral 用 `Sounds.craftFinish` 配 **pitch 1.7**（比 1.0 清脆得多）；Thaumcraft 在 infusion 期间每 65 刻播一次 `SoundsTC.infuser` |

### 1.2 它的构造与运动公式（关键）

`FlyTowardsPositionParticle.java:85-102`（运动本体）

```java
@Override
public void tick() {
    this.xo = this.x; this.yo = this.y; this.zo = this.z;
    if (this.age++ >= this.lifetime) {
        this.remove();
    } else {
        float pos = (float)this.age / this.lifetime;
        pos = 1.0F - pos;                 // 1 → 0
        float pp = 1.0F - pos;
        pp *= pp; pp *= pp;               // pp = pos^4
        this.x = this.xStart + this.xd * pos;
        this.y = this.yStart + this.yd * pos - pp * 1.2F;   // ← 唯一的重力项
        this.z = this.zStart + this.zd * pos;
    }
}
```

**逐条回答任务里的问题：**

- **它自带朝向玩家的速度吗？** —— **没有速度，也没有任何"朝向玩家"的逻辑。**
  `xd/yd/zd` **不是速度**，是 `pos` 的**位移偏移量**（`xd = startX - spawnX`）。
  粒子出生时就位于 `pos + offset`，然后用 `pos` 从 1 线性降到 0 一路插值回 `pos`。
- **`sendParticles` 的速度参数能引向别处吗？** —— **能，而且是它唯一的用法。**
  `ClientPacketListener.handleParticleEvent`（`D:\mcsrc\net\minecraft\client\multiplayer\ClientPacketListener.java:2312-2346`）
  把 `xa/ya/za` 原样当 `addParticle` 的 `xd/yd/zd` 传下去：

  ```java
  if (packet.getCount() == 0) {
      double xa = packet.getMaxSpeed() * packet.getXDist();
      double ya = packet.getMaxSpeed() * packet.getYDist();
      double za = packet.getMaxSpeed() * packet.getZDist();
      this.level.addParticle(packet.getParticle(), ...,
          packet.getX(), packet.getY(), packet.getZ(), xa, ya, za);
  } else {
      for (int i = 0; i < packet.getCount(); i++) {
          double xVarience = this.random.nextGaussian() * packet.getXDist();
          double yVarience = this.random.nextGaussian() * packet.getYDist();
          double zVarience = this.random.nextGaussian() * packet.getZDist();
          double xa = this.random.nextGaussian() * packet.getMaxSpeed();
          ...
          this.level.addParticle(packet.getParticle(), ...,
              packet.getX() + xVarience, packet.getY() + yVarience, packet.getZ() + zVarience,
              xa, ya, za);
      }
  }
  ```

  `ServerLevel.sendParticles` 的两条重载（`D:\mcsrc\net\minecraft\server\level\ServerLevel.java:1333-1365`）
  只是把这些数打包进 `ClientboundLevelParticlesPacket`（`xDist/yDist/zDist` 变 `float`，
  `count` 变 `int`，**没有别的地方会消耗速度**）。

  ⚠️ 所以要用 `sendParticles` 做"从玩家飞向雕像"，必须：
  **spawn 点 = 雕像**，**xor/yd/zd = （玩家位置 − 雕像位置）**。方向反了粒子就飞反。

### 1.3 原版附魔台自己是怎么用的（照抄这个用法就对了）

`D:\mcsrc\net\minecraft\world\level\block\EnchantingTableBlock.java:63-79`

**出生点在附魔台，偏移量指向书架 → 粒子从书架飞回附魔台。**
方向是"书架 → 附魔台"，不是"附魔台 → 书架"。这一点很多人会看反。

### 1.4 三个必须知道的限制

1. **寿命固定 25~40 刻**，位移多大都在这段时间内走完 → 长距离时**每刻位移很大、看起来是"跳"过去的**。
   算一下：位移 8 格 / 30 刻 ≈ 0.27 格/刻，还算能看；位移 30 格就完全不像"流动"了。
2. **`hasPhysics = false`**，不会被方块挡住（好事）。
3. **`count != 0` 的那条分支用的是 `nextGaussian()`**，只会做随机撒点，**不能给每颗粒子独立的精确终点**。
   要精确控制方向就得走 **`count = 0`** 分支（`maxSpeed` × `xDist/yDist/zDist` 合成一个统一偏移量），
   也就是 `ServerLevel.sendParticles(particle, false, false, x, y, z, 0, dx, dy, dz, 1.0)`。

### 1.5 还有两个"自带走位"的原版粒子（可能更有用）

| 粒子 | 实现类 | 机制 |
|---|---|---|
| `ParticleTypes.SCULK_CHARGE` | `SculkChargeParticle` | **真·速度**：`setParticleSpeed(xAux, yAux, zAux)`，`friction = 0.96F`，会自然减速。`D:\mcsrc\net\minecraft\client\particle\SculkChargeParticle.java:41-51` |
| `ParticleTypes.OMINOUS_SPAWNING` | `FlyStraightTowardsParticle` | 与 ENCHANT 同款"offset 插值"，但 `lifetime` 固定 25，带 start/end 颜色插值 |

`SculkChargeParticle` 那条路说明：**用"真速度"做飞向目标也是可行的**（设一次速度让它飞过去），
但因为没有转向，长距离会因摩擦衰减飞不到，反而不如插值稳。

**这是全篇最值得抄的一条**：`mana` 每刻都可能变，但它**不每刻发包**；
客户端只是把**收到的 `mana / manaToGet` 当成一个 0~1 的进度**，
再**用自己本地的 tick 时间驱动所有闪烁/旋转**（见 (c)）。
仪式开始/结束这种"状态跳变"才发一次包，并且顺手放了开始音效 `runeAltarStart`。

#### (b) 防重复触发 & 半途失效

- `cooldown`：合成后 `SET_COOLDOWN_EVENT = 60`，`addItem` 开头就 `if (cooldown > 0 ...) return false;`（`:82`）。
- `manaToGet != 0` 时也拒绝加料（`:98-100`），即**仪式中不能再塞东西**。
- **每刻重算配方**：`serverTick` 无条件调 `self.updateRecipe()`（`:192`），
  所以物品被拿走 / 配方不再匹配时，`manaToGet` 立刻归 0，仪式**自动中止**。
  没有"进度持久化"的概念——**它不需要持久化，因为进度是 mana，mana 存在 BE 里、
  而"能不能继续"是每刻现算的**。
- `cooldown` / `recipeKeepTicks` **不在** `writePacketNBT` 里 → 这两个值**不进存档也不进同步包**，
  靠 `blockEvent` 临时推给客户端。也就是说**服务器重启后冷却会丢**，作者接受了这个代价。

**要点**：
- **浮动的幅度 = 0.075 格，频率 = 每 5 刻一个正弦周期**（`sin(time/5)`），每件物品相位错开 `i*10`。

- `time` 用的是**客户端本地 tick（`ClientTickHandler.ticksInGame`）**，**完全不需要服务器同步**——
  这是关键设计：动画相位由客户端自己决定，服务端只负责"有没有东西放在上面"。

**还有一组"旋转符文立方体"**（`RunicAltarBlockEntityRenderer.java:104-145`），参数写得很清楚：

```java
private void renderSpinningCubes(PoseStack ms, MultiBufferSource buffers, int overlay, int cubes, int iters) {
    for (int curIter = iters; curIter > 0; curIter--) {
        final float modifier = 6F;
        final float rotationModifier = 0.2F;
        final float radiusBase = 0.35F;
        final float radiusMod = 0.05F;

        double ticks = ClientTickHandler.ticksInGame + ClientTickHandler.partialTicks - 1.3 * (iters - curIter);
        float offsetPerCube = 360 / cubes;

        ms.pushPose();
        ms.translate(-0.025F, 0.85F, -0.025F);
        for (int i = 0; i < cubes; i++) {
            float offset = offsetPerCube * i;
            float deg = (int) (ticks / rotationModifier % 360F + offset);
            float rad = VecHelper.toRadians(deg);
            float radiusX = (float) (radiusBase + radiusMod * Math.sin(ticks / modifier));  // 半径也呼吸
            float radiusZ = (float) (radiusBase + radiusMod * Math.cos(ticks / modifier));
            float x = (float) (radiusX * Math.cos(rad));
            float z = (float) (radiusZ * Math.sin(rad));
            float y = (float) Math.cos((ticks + 50 * i) / 5F) / 10F;                        // 上下浮动 ±0.1

            ms.pushPose();
```

- **速度传 0**（`0.0D, 0.0D, 0.0D`）——因为它知道 ENCHANT 的 aux 是**位移**不是速度，
  传 0 就等于"**把它当成一颗不动的贴图，直接摆在路径上的那个点**"，靠**撒点密度**造流向感；
- 路径是**起点到终点的直线**，`d4` 每次推进 `1.5~2.1` 格，所以一条 4 格的线大约撒 2~3 颗；
- **`d4 = r.nextDouble()` 让每条线的起点随机错开**，多撒几帧就看不出"同一批点"；
- **`isClientSide` 走 `addAlwaysVisibleParticle`，`ServerLevel` 走 `sendParticles`** —— 一份代码两端都能用。

> 对照 §1：ENCHANT 粒子自身也会"飞回来"，但 `beam` 只撒一个点、速度 0，
> 所以它飞不了（位移 0）—— **它根本不依赖粒子自身的运动**，纯粹靠撒点。
> 这就是"**更省的做法**"的答案：**沿路径插值撒原版粒子，靠密度造流向感。**

```java
        }
```

```java
        return;

    double posX = getX(), posY = getY(), posZ = getZ();
    double motionX = this.getDeltaMovement().x, motionY = ..., motionZ = ...;

    if (dest.getX() != 0 || dest.getY() != 0 || dest.getZ() != 0) {
        double targetX = dest.getX() + 0.5, targetY = dest.getY() + 0.5, targetZ = dest.getZ() + 0.5;
        Vec3 targetVector = new Vec3(targetX - posX, targetY - posY, targetZ - posZ);
        double length = targetVector.length();
        targetVector = targetVector.scale(0.3 / length);            // ★ 期望速度大小固定 0.3 格/刻
        double weight = 0;
        if (length <= 3) {
            weight = 0.9 * ((3.0 - length) / 3.0);                  // ★ 越近越"吸"，避免在目标附近抖动
        }
        motionX = (0.9 - weight) * motionX + (0.1 + weight) * targetVector.x;   // ★ 惯性 + 转向
        motionY = (0.9 - weight) * motionY + (0.1 + weight) * targetVector.y;
        motionZ = (0.9 - weight) * motionZ + (0.1 + weight) * targetVector.z;
    }
    posX += motionX; posY += motionY; posZ += motionZ;
    this.setPos(posX, posY, posZ);
    this.setDeltaMovement(motionX, motionY, motionZ);

    if (level.isClientSide && this.age > 1) {
        double deltaX = getX() - xOld, deltaY = getY() - yOld, deltaZ = getZ() - zOld;
        float dist = (float) (Math.sqrt(deltaX*deltaX + deltaY*deltaY + deltaZ*deltaZ) * 8.0f);
        for (double i = 0.0; i <= dist; i++) {                       // ★ 把这一帧的位移"铺满"粒子
            double coeff = (i / dist);
            level.addAlwaysVisibleParticle(GlowParticleData.createData(new ParticleColor(...)),
                true,
                (getX() + deltaX * coeff), (getY() + deltaY * coeff), (getZ() + deltaZ * coeff),
                0.0125f * (random.nextFloat() - 0.5f), ...);
        }
    }
}
```

**三条精髓**：
1. **`targetVector.scale(0.3 / length)`** —— 期望速度恒定 0.3 格/刻（≈ 6 格/秒），
   所以无论多远，**飞行时间都正比于距离**，速度感一致。
2. **`weight` 项**：距离 ≤3 格时逐渐加大"朝目标"的权重（最多 0.9），
   即**近处强吸附**，避免粒子在目标附近打转。这是"归航"类算法最容易踩的坑（终点抖动）。
3. **每帧沿 `old→new` 位移按 `×8` 的密度 `addAlwaysVisibleParticle` 插值撒点**
   —— **实体只负责"算轨迹"，视觉观感完全来自轨迹插值撒点**。
   这解释了为什么 AN 的投射物看起来是连续光带。

**逐条拆解（这就是"归航粒子"的核心算法）：**

| 步骤 | 代码 | 作用 |
|---|---|---|
| 寿命 = 距离 × 10 / 2 + rand | `base = dist * 10; lifetime = base/2 + rand(base)` | **距离越远活得越久**，保证能飞到 |
| 初始速度 | `nextGaussian() * 0.01` | 几乎静止，全靠转向力推进 |
| 阻尼 | `*= 0.985`（Y `*= 0.95`） | 速度不会无限累积 |
| 转向力 | `clamp = min(0.25, dist/15)` | **15 格以内按距离给力，超过就封顶 0.25** |
| 加速 | `v += dir * clamp` | 朝目标 |
| **夹紧** | `v = clamp(v, -clamp, +clamp)` | **三轴速度各自不超过 `clamp`** → 速度与距离成比例，越近越慢 |
| 抖动 | `v += gauss * 0.01` | 轨迹不呆板 |
| 缩小 | `dist < 2` → `scale *= 0.9` | 快到终点时收缩 |
| 可见性剔除 | 距摄像机 > 64 格 → `lifetime = 0` | 省渲染 |

**对比 ENCHANT 的"offset 插值"**：
- ENCHANT 是**匀速直线插值**（`pos` 线性 1→0），**没有任何抖动**，看起来"很规整"。
- `FXBoreSparkle` 是**带阻尼的加速归航 + 高斯抖动**，看起来"活"。
- **两者渲染的都是同一个"符文/字母"贴图族**，所以视觉上都可以说"像附魔台"。

### 3.2 抖动 / 浮动 / 旋转参数汇总

| 出处 | 幅度 | 频率 | partialTick | 备注 |
|---|---|---|---|---|
| Botania Runic Altar 物品浮动 | `0.075` 格 | `sin(time/5)`，每件相位 `i*10` | **直接加进 `time`** | 外加 `anglePer = 360/items` 公转 |
| Botania Runic Altar 符文立方体 | 半径呼吸 `±0.05`，Y `±0.1` | `sin(ticks/6)`、`cos(ticks/5)` | `+ partialTicks` | 转速 `ticks/0.2`（约 5°/刻） |
| AN Arcane Pedestal 物品 | 无浮动 | 自转 `(partialTick + ticksInGame)*3f` 度/刻 | 显式用 | 缩放 0.5 |
| AN Imbuement 物品 | 无浮动 | 自转 `(partialTick + ticksInGame)*3f` 度/刻 | 显式用 | 缩放 0.5 |
| AN Alteration Table 物品 | `smoothstepDerivative(...) * 0.0625` | `sin((ticksInGame+ticks)/20)` | 显式用 | 用了 **smoothstep 导数**做"停顿感"浮动 |
| AN Scribes 悬浮物品 | `((i%2==0?-i:i) * sin(ticks/60) * 0.0625)` | `sin(ticks/60)` | `ticks = partialTicks + ticksInGame` | 交替方向 |
| Thaumcraft 注魔台方块抖动 | **`0.01 × startUp × instability`**（最大 0.06 格） | **X `/15`、Y `/14`、Z `/13`** | 加进 `ticks` | 8 个副本相位 `a*10`；`instability` 随进度 1→6 |
| Thaumcraft 注魔台旋转 | Y `ticks%360 * startUp`；X `35*startUp`；Z `45*startUp` | —— | 加进 `ticks` | **用同一个 `startUp` 控制转速和倾角** |
| Thaumcraft 基座物品 | 无浮动（抬 0.75 格） | 自转 1°/刻 | 加进 `ticks` | 匀速，不抖 |
| Astral 共鸣祭坛悬浮 | `startY=-1.5 → endY=-0.5` 线性 | `prev/cur + partialTicks` 插值 | **规范的 prev/cur 插值** | 8 个符文相位 `spinDur/8*i`；结束 `tesrLocked` 归位 |

**给我们的抖动参数建议（从这张表推）**：
- **要"明显抖动"**（用例说"剧烈"）：把 Thaumcraft 的基准放大到 **0.02~0.04 格**，并且
- **三轴用不同分母**（比如 `/10`、`/9`、`/11`）→ 才不会看起来像整体平移；
- **一定要有包络**（`startUp` 指数缓入 / `instability` 随进度上升），否则"一直抖"很廉价；
- **`partialTick` 必须用**，否则抖动会以 20Hz 跳格，看起来像卡顿而不是抖。

### 3.3 "粒子飞向目标"的四种手法

| 手法 | 代表 | 网络成本 | 长距离表现 | 实现难度 |
|---|---|---|---|---|
| **① 沿直线插值撒点** | AN `ParticleUtil.beam`、Botania `doParticleBeam`、`SPARK_NET_INDICATOR` | **0**（客户端自己算）/ 或 1 包线路 | **好**（步长固定，点数随距离线性增长） | ★ 最低 |
| **② 客户端粒子 + 每刻服务端发包指定源/终点** | TC `PacketFXInfusionSource` + `sourceFX` | 20 字节 **×1 次**（之后客户端自己维持 N 刻） | 好 | ★★ |
| **③ 自写"自带终点"的粒子类** | TC `FXBoreSparkle`、AN `ParticleLine` | 1 包/粒子（`ParticleOptions` 携带终点） | **最好**（可加抖动/阻尼/曲线） | ★★★ |

**⭐ 对我们最合适的是 ②**：服务端在仪式开始时**发一次**"从玩家到雕像"的包，客户端**自己维持 60 刻的粒子流**。

```java
public class ShelfRenderer implements BlockEntityRenderer<ShelfBlockEntity, ShelfRenderState> {
    private final ItemModelResolver itemModelResolver;

    public ShelfRenderer(BlockEntityRendererProvider.Context context) {
        this.itemModelResolver = context.itemModelResolver();          // ★ 从 Context 取
    }

    public ShelfRenderState createRenderState() { return new ShelfRenderState(); }

    public void extractRenderState(ShelfBlockEntity blockEntity, ShelfRenderState state, float partialTicks,
                                   Vec3 cameraPosition, ModelFeatureRenderer.@Nullable CrumblingOverlay breakProgress) {
        BlockEntityRenderer.super.extractRenderState(blockEntity, state, partialTicks, cameraPosition, breakProgress);
        state.alignToBottom = blockEntity.getAlignItemsToBottom();
        state.facing = blockEntity.getBlockState().getValue(ShelfBlock.FACING);
        NonNullList<ItemStack> items = blockEntity.getItems();
        int seed = HashCommon.long2int(blockEntity.getBlockPos().asLong());      // ★ seed 从坐标来

        for (int slot = 0; slot < items.size(); slot++) {
            ItemStack itemStack = items.get(slot);
            if (!itemStack.isEmpty()) {
                ItemStackRenderState itemStackRenderState = new ItemStackRenderState();     // ★ 在 extract 里 new
                this.itemModelResolver.updateForTopItem(itemStackRenderState, itemStack,
                        ItemDisplayContext.ON_SHELF, blockEntity.level(), blockEntity, seed + slot);
                state.items[slot] = itemStackRenderState;
            }
        }
    }

    public void submit(ShelfRenderState state, PoseStack poseStack, SubmitNodeCollector submitNodeCollector, CameraRenderState camera) {
        float yRot = state.facing.getAxis().isHorizontal() ? -state.facing.toYRot() : 180.0F;
        for (int slot = 0; slot < state.items.length; slot++) {
            ItemStackRenderState itemStackRenderState = state.items[slot];
            if (itemStackRenderState != null) {
                this.submitItem(state, itemStackRenderState, poseStack, submitNodeCollector, slot, yRot);
            }
        }
    }

    private void submitItem(ShelfRenderState state, ItemStackRenderState itemStackRenderState, PoseStack poseStack,
                            SubmitNodeCollector submitNodeCollector, int slot, float yRot) {
        poseStack.pushPose();
        poseStack.translate(0.5F, 0.5F, 0.5F);
        poseStack.mulPose(Axis.YP.rotationDegrees(yRot));
        poseStack.translate(itemOffset);
        poseStack.scale(0.25F, 0.25F, 0.25F);
        AABB box = itemStackRenderState.getModelBoundingBox();
        double offsetY = -box.minY;                                              // ★ 用包围盒对齐底部
        poseStack.translate(0.0, offsetY, 0.0);

        itemStackRenderState.submit(poseStack, submitNodeCollector, state.lightCoords, OverlayTexture.NO_OVERLAY, 0);   // ★★ 提交
        poseStack.popPose();
    }
}
```

**⭐ 三条铁律**：
1. **`extractRenderState` 每帧都会调用，且带 `blockEntity`** → **所有"读 BE 数据"和"创建 `ItemStackRenderState`"都在这里做**；
2. **`submit` 里只能提交，不能再读 BE**（`state` 里该有的都得在 extract 阶段装好）→
   **所以 `StatueRenderState` 里要放：`containedStack` 的 `ItemStackRenderState`、仪式剩余 tick、玩家位置等**；
3. **动画的时间基准**：`extractRenderState` 只给 `partialTicks`，**没给 `gameTime`**。
   要拿时间基准就得：
   - 在 `extractRenderState` 里从 `blockEntity.getLevel().getGameTime()` 读出（推荐），或
   - 用 `Minecraft.getInstance().level.getGameTime()`（不推荐，耦合），或
   - **在 `state` 里存一个 `float animationTime = level.getGameTime() + partialTicks`**（推荐）。

   > **注意 `ShelfRenderer` 里没有出现 partialTick 驱动的旋转**，也就是说 26.1.2 的原版物品渲染不带自转。
   > **自转/抖动必须我们自己加**：在 `submit` 里 `poseStack.mulPose(Axis.YP.rotationDegrees(state.animationTime * 3f))`
   > 和 `poseStack.translate(0, state.jitterY, 0)`。

```java
    // 起始音（可选）
    this.level.playSound(null, this.worldPosition, SoundEvents.ILLUSIONER_CAST_SPELL,

public static void serverTick(Level level, BlockPos pos, BlockState state, EmotionStatueBlockEntity be) {
    if (be.ritualTicks <= 0) return;

    Entity src = be.ritualPlayerId >= 0 ? level.getEntity(be.ritualPlayerId) : null;
    if (src == null || !src.isAlive() || src.distanceToSqr(Vec3.atCenterOf(pos)) > 64 * 64) {
        be.abortRitual("源消失/太远");             // ★★ 防半途卡死：源不在就直接中止
        return;
    }

    if (--be.ritualTicks == 0) {
        be.finishRitual();                        // 变法杖 + 留在台座 + 播"丁"
    }
    // 注意：故意不 setChanged()/不发包 —— 进度客户端自己数
}

private void abortRitual(String why) {
    this.ritualTicks = 0;
    this.ritualPlayerId = -1;
    this.setChanged();
    this.level.sendBlockUpdated(this.worldPosition, this.getBlockState(), this.getBlockState(), 3);
}

private void finishRitual() {
    this.contained = new ItemStack(ModItems.EMOTION_STAFF.get());   // ★ 留在台座（contained 就是台座内容）
    this.ritualPlayerId = -1;
    this.setChanged();
    this.level.sendBlockUpdated(this.worldPosition, this.getBlockState(), this.getBlockState(), 3);
    this.level.playSound(null, this.worldPosition, SoundEvents.AMETHYST_BLOCK_CHIME,
            SoundSource.BLOCKS, 1.5F, 1.7F);                        // ★★ "丁"
    // 完成爆发粒子（服务端发，必定到达）
    if (this.level instanceof ServerLevel sl) {
        sl.sendParticles(ParticleTypes.END_ROD,
                pos.getX() + 0.5, pos.getY() + 1.2, pos.getZ() + 0.5,
                25, 0.35, 0.35, 0.35, 0.05);
    }
}
```

```java
    BlockEntityRenderer.super.extractRenderState(be, state, partialTicks, cameraPos, breakProgress);

    Level lvl = be.getLevel();
    float time = (lvl == null ? 0F : lvl.getGameTime()) + partialTicks;
    state.animationTime = time;

    // ── 抖动幅度：以"剩余 tick"做包络，越接近完成抖得越凶
    int remain = be.getRitualTicks();
    state.isRitualActive = remain > 0;
    if (state.isRitualActive) {
        float progress = 1.0F - (float) remain / (float) EmotionStatueBlockEntity.RITUAL_TICKS;
        float envelope = 0.35F + 0.65F * progress;          // 0.35 → 1.0
        // ★★ 三轴不同分母 + 大相位错开 = 看起来像"抖"而不是"平移"
        state.jitterX = Mth.sin(time / 10.0F) * 0.030F * envelope;
        state.jitterY = Mth.sin(time /  9.0F) * 0.030F * envelope;
        state.jitterZ = Mth.sin(time / 11.0F) * 0.030F * envelope;
        state.extraSpin = 6.0F * progress;                  // 越到后面转得越快（度/刻）

        // ── ★★ 粒子流：从玩家流向雕像（原版 ENCHANT，靠"沿线撒点"造流向感）
        Entity src = lvl.getEntity(be.getRitualPlayerId());
        if (src != null) {
            Vec3 from = src.getEyePosition(partialTicks);                       // 玩家眼睛
            Vec3 to   = Vec3.atCenterOf(be.getBlockPos()).add(0, 1.0, 0);       // 雕像台座上方
            spawnFlow(lvl, from, to, time);
        }
    } else {
        state.jitterX = state.jitterY = state.jitterZ = 0F;
        state.extraSpin = 0F;
    }

/** 沿线撒 ENCHANT：位移参数必须传 0（ENCHANT 的 aux 是"位移"不是"速度"，见 §1） */
private void spawnFlow(Level level, Vec3 from, Vec3 to, float time) {
    Vec3 diff = to.subtract(from);
    double len = diff.length();
    if (len < 0.05) return;
    Vec3 dir = diff.scale(1.0 / len);

    double step = 0.6;                                  // 每 0.6 格一颗
    // ★ 起点相位随时间推进 → 肉眼看到"在流"而不是"一片静止的点"
    double offset = (time * 0.25) % step;
    // ★ 分几股，避免所有粒子挤在一条直线上
    int strands = 3;
    for (int s = 0; s < strands; s++) {
        double lateral = (s - (strands - 1) / 2.0) * 0.25;
        Vec3 perp = new Vec3(-dir.z, 0, dir.x).scale(lateral);          // 水平垂直方向
        for (double d = offset; d < len; d += step) {
            Vec3 p = from.add(dir.scale(d)).add(perp);
            // 少量随机抖动，看起来不像"一条几何线"
            level.addParticle(ParticleTypes.ENCHANT,
                    p.x + (level.random.nextDouble() - 0.5) * 0.15,
                    p.y + (level.random.nextDouble() - 0.5) * 0.15,
                    p.z + (level.random.nextDouble() - 0.5) * 0.15,
                    0.0, 0.0, 0.0);                                  // ★★ 位移传 0
        }
    }
}
```

#### 【方案 B】"稳妥"：抄 Thaumcraft —— 仪式开始时发一次"源→目标"的包，客户端自己维持 60 刻

**适用**：不想让 `extractRenderState` 承担"撒粒子"的副作用，或者粒子源不止一个（多个玩家/多个物品）。

**思路**：完全照搬 TC 的 `PacketFXInfusionSource` + `sourceFX`，但用 26.1.2 的 `CustomPacketPayload`。

```java
// ── 客户端缓存（等价于 TC 的 TileInfusionMatrix.sourceFX）
public final class ClientFlowCache {
    private static final Map<BlockPos, Flow> FLOWS = new HashMap<>();

    private record Flow(int sourceEntityId, int ticks, int totalTicks) {}

    public static void start(RitualFlowPayload p) {
        FLOWS.put(p.statuePos(), new Flow(p.sourceEntityId(), p.totalTicks(), p.totalTicks()));
    }

    /** 在 StatueRenderer.extractRenderState 里每帧调一次 */
    public static void tickAndRender(Level level, float partialTicks, float time) {
        Iterator<Map.Entry<BlockPos, Flow>> it = FLOWS.entrySet().iterator();
        while (it.hasNext()) {
            var e = it.next();
            Flow f = e.getValue();
            BlockPos statuePos = e.getKey();

            Entity src = level.getEntity(f.sourceEntityId());
            if (src == null || f.ticks() <= 0 || !level.isLoaded(statuePos)) {
                it.remove();                                    // ★★ 双保险清理，绝不卡死
                continue;
            }
            Vec3 from = src.getEyePosition(partialTicks);
            Vec3 to   = Vec3.atCenterOf(statuePos).add(0, 1.0, 0);
            // ★ 进度来自"这个缓存自己的 ticks"，和雕像 BE 解耦
            float progress = 1.0F - (float) f.ticks() / (float) f.totalTicks();
            spawnFlow(level, from, to, time, progress);         // 同方案 A 的 spawnFlow
            e.setValue(new Flow(f.sourceEntityId(), f.ticks() - 1, f.totalTicks()));
        }
    }
}
```

| ✅ 好处 | ⚠️ 代价 |
|---|---|
| **粒子撒点从 BER 里搬走**，BER 只管渲染 → 职责清晰 | 要写一个 `CustomPacketPayload` + 注册 |
| **客户端"自己维持 60 刻"**，服务端**只发一次包** | 多一套"客户端缓存要靠 tick 递减来清理"的逻辑 |
| 天然支持**多个源**（每个源一个 key），将来加"多个玩家一起唤醒"不用改架构 | 客户端缓存和 BE 状态可能不同步（包丢了就一直有/一直没有）——所以**方案 B 建议同时保留 A 的 `ritualTicks` 同步**，两者互为兜底 |
| **`level.getEntity(id)` 拿源位置**，玩家会动也能跟上（TC 就是这么做的） | —— |

> **⚠️ 用 `int entityId` 而不是 `UUID` 的重要理由**：`UUID` 是 16 字节且需要 `ServerLevel.getEntity(UUID)`
> 在 26.1.2 里查表；**`int` id 只需 4 字节（varint 更少）**，而且 **`Level.getEntity(int)` 是 O(1)**
> （Astral 也用 `entityIdActive` 而不是 UUID，`TileAttunementAltar.java:118`）。
> **唯一注意**：实体 id 只在"客户端已知该实体的范围"内有效 —— 所以**必须保证包发给了会看到雕像的玩家**
> （用 `PacketDistributor.sendToPlayersNear(...)`），否则 `level.getEntity(id)` 返回 `null`。
> **这正好是 TC 的 `PacketFXInfusionSource` 要挂在 client world 的 tile 上的原因。**

```java
// ── 2. 客户端粒子：归航（参数全部来自 §2.3(c) 的 FXBoreSparkle）
public class SeekParticle extends SingleQuadParticle {
    private final Vec3 target;

    protected SeekParticle(ClientLevel level, double x, double y, double z,
                           double vx, double vy, double vz, Vec3 target, SpriteSet sprites) {
        super(level, x, y, z, vx, vy, vz, sprites.get(level.random));   // ★ 这里 aux 是真初速
        this.target = target;
        // ★ 寿命 ∝ 距离（FXBoreSparkle: base = dist*10; lifetime = base/2 + rand(base)）
        double dist = target.distanceTo(new Vec3(x, y, z));
        this.lifetime = (int) (dist * 5) / 2 + this.random.nextInt(Math.max(1, (int) (dist * 5)));
        this.hasPhysics = false;
        this.friction = 0.985F;
        this.quadSize = 0.1F;
    }

    @Override
    protected int getLightColor(float partialTick) { return 0xF000F0; }   // 满亮度（抄 AN ParticleLine）

    @Override
    public void tick() {
        this.xo = this.x; this.yo = this.y; this.zo = this.z;
        if (this.age++ >= this.lifetime) { this.remove(); return; }

        // 阻尼（Y 更强，抄 FXBoreSparkle）
        this.xd *= 0.985; this.yd *= 0.95; this.zd *= 0.985;

        double dx = target.x - this.x, dy = target.y - this.y, dz = target.z - this.z;
        double d = Math.sqrt(dx*dx + dy*dy + dz*dz);
        if (d < 0.3) { this.remove(); return; }
        double clamp = Math.min(0.25, d / 15.0);                 // ★ 转向力上限，近处变弱
        if (d < 2.0) this.quadSize *= 0.9F;                       // ★ 快到终点缩小
        dx /= d; dy /= d; dz /= d;
        this.xd += dx * clamp; this.yd += dy * clamp; this.zd += dz * clamp;
        // ★ 三轴各自夹到 ±clamp
        this.xd = Mth.clamp(this.xd, -clamp, clamp);
        this.yd = Mth.clamp(this.yd, -clamp, clamp);
        this.zd = Mth.clamp(this.zd, -clamp, clamp);
        // ★ 高斯抖动 → 轨迹有"游丝"感
        this.xd += this.random.nextGaussian() * 0.01;
        this.yd += this.random.nextGaussian() * 0.01;
        this.zd += this.random.nextGaussian() * 0.01;

        this.move(this.xd, this.yd, this.zd);
    }
}
```

### 4.3 我的推荐

**分两步走：先落方案 A，看效果再决定要不要演进到 B/C。**

理由：

1. **方案 A 已经能满足用例的全部 5 条**：
   - 粒子流 ✅（ENCHANT 沿路径撒点，`extractRenderState` 里做）
   - 剧烈抖动 ✅（三轴不同频率正弦 + 进度包络 + `partialTick`）
   - 3 秒后"丁" ✅（`AMETHYST_BLOCK_CHIME` + pitch 1.7，或自制音效）
   - 物品留台座 ✅（`contained` 就是台座内容，`finishRitual()` 里直接替换）
   - 禁重复触发 ✅（`ritualTicks > 0` 早退）
2. **A 不引入任何新的注册项/包类型**，改动面只有 `EmotionStatueBlockEntity` + `StatueRenderer` + `StatueRenderState` 三个文件。
3. **A → B 是纯增量**（把撒点逻辑从 BER 搬到 `ClientFlowCache`），
   **A → C 也是纯增量**（把 `level.addParticle(ParticleTypes.ENCHANT, ...)` 换成自定义粒子）。
   所以**不值得一开始就上 C**。
4. **唯一建议在 A 里就做对的**：
   - **`extractRenderState` 里只做"读 + 组装 state + 撒粒子"，`submit` 里只做"摆 pose + submit"** —— 保持这个纪律，
     将来如果 NeoForge 改了 `extractRenderState` 的调用时机（比如加"离屏时也调用"），迁移成本最小；
   - **`ritualPlayerId` 用 `int` 而不是 `UUID`**（存进同步 NBT 时省空间，且 `Level.getEntity(int)` 是 O(1)）；
   - **"源不在/太远/区块卸载"三种情况的清理一定要写**（抄 AN 的 `UNLOADED_TO_CHUNK → DISCARDED` 思路）；
   - **绝对不要让 `ritualTicks` 只在客户端数**（客户端 tick 会在暂停/断线时停）——
     以**服务端 tick 为准，客户端只拿一个"剩余刻数快照"然后自己插值**。

**当且仅当以下情况发生，才升级到 B 或 C**：

- 粒子源不止一个（"多个玩家一起唤醒"）→ **升 B**；
- 玩家和雕像距离可能超过 ~10 格，"撒点"开始显得稀疏/像一条虚线 → **升 C**（归航粒子会自适应距离）；
- 想做"粒子从玩家身上螺旋飞出去再撞进雕像"这种曲线 → **只能升 C**。
