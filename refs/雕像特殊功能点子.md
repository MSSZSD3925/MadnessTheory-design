## 2　紫颂花「存储数值在 0 时无中生有」怎么落地

### 2.1 先回答"数值存在哪"

模组里有**两个**情绪数值，不要混：

| 数值 | 存放位置 | 键/字段 | 上限 |
|---|---|---|---|
| **法杖里的情绪** | 物品数据组件 `ModComponents.EMOTION`（`ModComponents.java:24-27`） | `EmotionPayload.amount`（`EmotionPayload.java:31`） | `effectiveCapacity()`（`:100-108`） |
| **玩家的心绪存储** | 玩家附件 `MoodAttachments.MOOD_DATA`（`MoodAttachments.java:51-53`）里的 `List<String> moods`（`:161`） | 每行 `"心绪id|属性id|数量"`，编解码见 `EmotionMoodStore` 的 `encode/part`（`:162-189`） | **每类各自 150**（`EmotionMoodStore.CAPACITY`，`:34`） |

"0 时无中生有"里的"存储"，我判断指的是**后者（玩家的心绪池）**——
因为只有在一个**空池子**上"无中生有"才像一条特性；在法杖上它只是"多了几点"。
但我把两边的落点都给出来，供作者选。

### 2.2 在哪个环节发生（三个落点，推荐第一个）

**⚠️ 铁律：绝不要放在每帧/每 tick 被调用的读取路径里。**
`EmotionMoodStore.amountAll` / `decodeTotals` 被 HUD（`client/MoodHudLayer`）每帧调用，
在那里加副作用会变成**每帧加一点**。

**落点 ①（推荐）：玩家 tick 上的「空池唤醒」，事件驱动 + 冷却**
- 位置：`EmotionMoodStore` 新增 `wakeEmptyPools(data, rng, attrId)`，
  由玩家 tick 挂点调用（现成的挂点见 `DreamSession.onPlayerTick`，`DreamSession.java:233`）。
- 三个条件同时成立才触发：
  1. 玩家主手/副手持有一根**紫颂花法杖**。判据建议用**材质**：
     `StatueMaterial.byIdOrNull(p.materialId()).kind() == CHORUS`
     （`StatueMaterial.kind()`，`StatueMaterial.java:198`；`materialId` 在 `EmotionPayload.java:45`，
     由 `GuideBookItem.java:346` 写入）—— 这比按 `kindId` 判更贴"属于**法杖**的特色"。
  2. 该杖 `payload.attrId()` 对应的心绪里有**当前为 0** 的类。
  3. 冷却到期 —— 建议 **600 刻（30 秒）**一次，冷却存成 `MoodData` 的新字段
     （**新持久字段必须"可选 + 默认值"**，照 `MoodAttachments.java:290-294` 里 `moods` 的写法）。
- 效果：随机挑一类**当前为 0** 的心绪，`EmotionMoodStore.add(data, mood, p.attrId(), 1)`。
  **1 点**，不要更多。

**落点 ②：绽裂结算时往空池倾斜**
- `RitualEffects.burst()` 现在是"每类平均 + ±20% 浮动"（`:336-345`）。
  可以让**外围是紫颂花**时把"当前为 0 的类"多分一点。
- 优点：完全落在已有代码里（`per` 的计算处），零新状态、零 tick 开销。
- 缺点：语义是"分配倾斜"而非"无中生有"，弱一档。

**落点 ③：空杖自己起搏（最贴"输入随机"的另一半，但风险最高）**
- 位置：`EmotionStaffItem.use()`（`:63`）之前，或 `appendHoverText`（`:230`）。
- 效果：一根**空的**紫颂花杖每隔 N 刻自己涨 1 点（受 `effectiveCapacity()` 封顶）。
- 风险：它会让"空杖"变成**可无限等待的资源源**。

### 2.3 上限怎么控（三条）

1. **心绪侧必须吃 150 的硬上限** —— 直接调 `EmotionMoodStore.add(...)`，
   它内部就是 `min(n, freeSpaceFor(...))`（`:87-88`）。**不要自己写加法**，
   这样永远不会超上限，且与绽裂的溢出转经验逻辑天然一致。
2. **必须同时有「冷却」与「仅 0 时」两个闸门。**
   只写"为 0 就 +1"，玩家**什么都不做**也能把 10 类全部顶到 150 ——
   那就直接推翻了"心绪需要攒两次"的节奏设计（`EmotionMoodStore.java:19-21` 写明
   150 与绽裂 ×1.5 是配套的）。建议再加"每类单日封顶"或"只在玩家做别的事时顺手给 1 点"。
3. **永不越过玩家已有的量** —— `add` 只往"最小"方向给，天然只从 0 起步。

- **落点**：`EmotionMoodStore.freeSpaceFor`（`:50`）/ `add`（`:83`）**复用不改**；

## 3　点子 4 重写后的完整设计（紫水晶 · 属性洗炼）

### 3.1 它是"第四种仪式"还是"升华/沉坠的变体"

**我的建议：做成「让升华/沉坠多一条洗炼分支」，不新增第四种结构。**
理由是**结构判定层本来就在做这件事**，看 `RitualStructure.match` 的判定顺序（`:106-129`）：

```
① 中心是雕像 + 台座上有东西
② tryBurst（八尊朝外）      → 不成立就继续
③ tryInward(wood=true)      → 四尊朝内 + 木头类 → SUBLIMATION
④ tryInward(wood=false)     → 四尊朝内 + 石头类 → SINKING
```

**关键事实（本次新核对）**：`isWood`（`:206-210`）与 `isStone`（`:213-217`）都是**硬编码白名单**，
新的紫水晶种类**不在里面** —— 而 `EmotionStatueKind.java:70-72` 的注释自己写明了这件事。
所以**紫水晶雕像只能当中心**；两侧（四尊朝内）仍须从现有 6 种里选。**这正好够用**：

> **洗炼 = 中心是紫水晶雕像的升华或沉坠。**
> 极性方向照旧（木类外围 → 升华取正面；石类外围 → 沉坠取负面）。
> **洗炼只改「属性」，不改「取哪一半」。**

好处：**结构判定零改动、`RitualKind` 不用加、`RitualStructure.Result` 不用动**，
全部落在效果层 —— 与第一轮"最稳的落点是 `RitualEffects.inject`"的结论一致。

### 3.2 "把记录的属性洗成外部雕像的同类属性" —— 是哪一尊

作者原话是"外部雕像"，**不是**中心。所以：

- **不是**中心那尊（中心就是紫水晶基座，用它等于"一律洗成幽闭属性"，玩家没有选择空间）。
- **应当是外围那四尊的属性** —— 直接用**现成字段** `RitualStructure.Result.outerKind()`
  （`:64`），`tryInward` 会填好它（`:199-200`）。四尊本来就强制同类（`:185-188`），
  因此 `outerKind().attribute()` 是**单值、无歧义**，**不需要动 `Result`**。

于是玩家能做的事很清楚：
> 「手头这条记录是**自然**属性，我想要**下界**属性 → 摆四尊下界岩石（沉坠结构），
>   中心放紫水晶 → 洗成下界属性。」

**它创造的东西**：属性层是**平方**的（外围 × 中心，`RitualEffects.java:179-184`），
所以「记录属性」是整条链上**玩家唯一无法自己决定的输入**。洗炼第一次让玩家控制这个输入 ——
配合已有的材质表，等于"我可以把任何一条记录变成任何材质的同类"。

### 3.3 ×0.8 乘在哪一步

**乘在"提取出的那一份"上，且在偏好之前**，即 `RitualEffects.inject()` 里：

```
现在：int total  = (int) Math.round(amount * share);                        // :139
      ...
      double loss = r.injectionLoss() * centerKind.injectionRatio() * pref; // :186
      int injected = (int) Math.max(1, Math.round(total * loss));           // :187

洗炼：total = (int) Math.round(amount * share * 0.8);   ← 只改这一行
```

**为什么乘在 `total` 而不是乘在 `loss` 上**：乘在 `loss` 上会与"外围/中心损耗 × 偏好"混在一起，
玩家在聊天栏看到的三因数拆解（`:234-237`）会多出一个说不清来源的 0.8；
乘在 `total` 上，玩家看到的是"**提取出的情绪少了 20%**"，语义干净，
而且**保住了 `Math.max(1, ...)` 的 1 点下限**（`:187`）不会因 0.8 变成 0。

**建议一并改提示**：聊天栏现在打「从这条记录中提取 X 点」（`:225-229`），
洗炼时应改成「洗炼：把「自然」洗成「下界」，提取 X 点（×0.8）」，
否则玩家无法从反馈里看出 0.8 花在哪。

### 3.5 与三种既有仪式的关系（收束表）

| | 升华 | 沉坠 | 绽裂 | **洗炼（新）** |
|---|---|---|---|---|
| 结构 | 中心任意 + 四尊朝内（木类） | 中心任意 + 四尊朝内（石类） | 中心任意 + 八尊朝外 | **中心 = 紫水晶 + 四尊朝内（木或石）** |
| 取的极性 | 正面 | 负面 | 不涉及 | **照旧（看外围类别）** |
| 改什么 | 杖里的量 | 杖里的量 | 杖 → 心绪 | **记录属性 → 外围雕像的属性** |
| 代价 | 1 条记录 | 1 条记录 | 0 条记录 | 1 条记录 **+ ×0.8** |
| 新增结构判定 | — | — | — | **不需要**（复用 `tryInward`） |

**判定优先级**：因为洗炼**复用** `tryInward`，顺序天然是"先绽裂、再升华/沉坠"，
**洗炼不需要新优先级** —— 它是在"已确定是升华还是沉坠"之后，再看**中心是不是紫水晶**。
实现上就是 `inject()` 里的一个 `if`。

## 4　下界砖新方向的完整设计（情绪方块 / 熔炼 → 梦境房间原料）

### 4.1 最关键的发现：它几乎不需要新方块

作者说这些方块要成为"**梦境维度中房间的原料**"。本轮读了梦境那一半的代码，
**这条链的接口早就存在，而且名字就是为它留的**：

| 事实 | 位置 |
|---|---|
| 房间每一面都由「**心绪块（明）/（暗）**」铺成 | `DreamRoom.applyFace`（`:159-170`）用 `ModBlocks.MOOD_LIGHT` / `MOOD_DARK` |
| 明块亮度 **15**、暗块亮度 **5** | `ModBlocks.java:52-63` |
| 组件字符画只认 **L / D**（外加 R/N/X 三种"跟着进度走"的记号） | `DreamPiece` 的 `Slot`/`Base`/`at()`（`DreamPiece.java:34-43`、`:90-96`）；`DreamRoom.applyFace` 的 switch（`:198-208`） |
| 搭建 → 保存 → 复用的完整通路 | `/madnesstheory piece save`（`MadnessCommands.savePiece`，`:590-624`）→ `DreamRoom.capturePad`（`:321-333`）→ `symbolOf`（`:336-343`） |
| 生成时按组件安排各面 | `DreamPieces.plan`（`:166-185`）、`WINDOW=0.3`（`:44`）、`WALL_GATE/FRAME_GATE`（`:46-48`） |

**结论：**

> **「情绪方块」= 现有的 `mood_light` / `mood_dark` 两种方块本身。**
> 它们现在**只能靠创造模式拿到**（`ModBlocks.java:65-68` 只注册了 BlockItem，没有任何获取途径）。
> 第一轮读到它们是"早期实验方块"，第二阶段方案 §7 的 Q5 也问过；
> 作者当时答"是梦境维度小房间的标记方块，与情绪/心绪系统无关，本阶段不动它们"。
> **这条答复现在被新方向推翻了** —— 它们**正是**"情绪方块"，当时缺的只是**生产手段**，
> 而熔炼仪式补的就是这个手段。

**这样做的成本几乎为零**：不新增方块、不新增模型/贴图/方块状态（**零美术**）；
`piece save` 立刻能捕获（`symbolOf` 已认它们，`:337-338`）；
`room build` / `applyFace` 立刻能摆（`:199-200`）；`isMood`（`:303-305`）与 `collapse`（`:282`）天然覆盖。

### 4.2 "十种心绪"怎么办（唯一需要作者拍板的分叉）

**A 案（推荐 · 零美术）**：**只做两极** —— 正性情绪 → `mood_light`；负性情绪 → `mood_dark`。
"纯粹"= **极性纯粹**（与绽裂的"单一极性"同一个词、同一个世界观）。
十种心绪不进方块，仍只活在玩家存储里（HUD + 书）。代价：房间里看不出"这是快乐还是安宁"。

**B 案（心绪十色 · 要美术）**：让方块带心绪种类。
- **不要新注册 20 个方块**。最省的落法是给 `MOOD_LIGHT`/`MOOD_DARK` **各加一个
  `EnumProperty<EmotionMood>`**（照 `EmotionStatueBlock` 的三属性做法，`EmotionStatueBlock.java:46-61`）：
  方块状态 1 → **各 10 个**（明 10 + 暗 10 = 20 variants）。注册名仍只有 2 个。
- 随之要改：`symbolOf`（`:336`）—— 现在只有 L/D 两个字母可用，
  要么把字符集扩到 20 个，要么**只按极性映射**（那就退化成 A 案）；
  `applyFace` 的 switch（`:198-208`）要扩；**并且要考虑旧组件兼容**
  （`.json` 里的 L/D 必须永远有效，而组件有数据包与玩家本地文件两个来源，`DreamPieces.load` `:94-136`）。

**我的建议：A 案先落地，B 案等 A 跑通、且玩家真的需要「房间里看出种类」时再做。**

### 4.3 熔炼仪式的结构与消耗

| 项 | 设计 | 依据 / 代价 |
|---|---|---|
| 中心 | **下界砖雕像**，台座上插**法杖** | 与升华/沉坠同形，`match` 的入口条件已满足（`:99-104`） |
| 外围 | **四尊朝内、同类**，来自**新的一类**（建议称"熔炉类"） | **本方案唯一的真改动**：`isWood`/`isStone` 是硬编码白名单（`:206-217`），须新增第三个方法 + `tryInward` 加一个"类别"维度 |
| 建议的外围种类 | **黑曜石 / 哭泣的黑曜石**（新 kind `OBSIDIAN`） | 耐高温 + 下界熔炉意象；且这两个方块**目前完全没被使用过** |
| 触发 | 手持指南书右键中心 | 与三个既有仪式一致（`GuideBookItem.useOn`，`:268-279`） |
| 时长 | 建议 **200 刻（10 秒）**，短于升华/沉坠的 600 刻 | 绽裂现在是**零时长**（`RitualEffects.java:278` 即时结算，类注释 `:46` 点明），多一档 10 秒更有层次 |
| 消耗 | **清空法杖里的情绪**（`payload.drained()`，`EmotionPayload.java:91`）；**不消耗记录** | 与绽裂一致 —— 它的输入是杖，不是书 |

**入场条件（建议）**：
- **不要求超容量**（那是绽裂的入场券，`RitualEffects.java:287`），
  但要求含量达门槛：建议 `amount >= 8`（最低档一条记录的量，`GuideBookItem.java:393`）。
  这样两个消费法杖的仪式分工清楚：
  **绽裂 = 把超量的单一极性拆成心绪；熔炼 = 把任意含量的混合情绪铸成建材。**
- **允许正负参半** —— 这是熔炼**相对绽裂最大的互补价值**：
  绽裂明确拒绝参半（`:296-305`，"杖里的情绪正负参半，拆不开"），
  而熔炼**按比例拆成明暗两种方块**，参半的杖第一次有了用处。

### 4.4 熔炼规则与转换比（大概数）

```
blocks = clamp(floor(amount / 8), 1, 32)     // 总量
lit    = (blocks + 1) / 2 ... 见下
（正确写法：lit = round(blocks * ratio)，dark = blocks - lit，ratio 取 payload.ratio()）
```

- **8 点 / 块**：最低档一条记录（8 点）产 1 块；最高档（32 点）产 4 块；
  一根灌到 336 点的杖产 32 块（正好到上限）。
- **上限 32 / 次** —— 必须有，否则"一次性把房间砌满"，会让梦境建造失去劳作感。
- **参半示例**：`amount = 40`、`ratio = 0.5` → `blocks = 5` → 明 3 / 暗 2。
  ⚠️ 用 `round` 在 0.5 处有偏向，建议写确定性分配（例如 `dark = blocks / 2; lit = blocks - dark`），
  避免同一批方块数量随舍入方向漂移。
- **外围同类加成**：建议**沿用绽裂的写法**（`RitualEffects.java:317-326`，只取外围一层
  `multiplierFor(mAttr, eAttr, positive)`），**不要**用升华/沉坠的两层 —— 熔炼的主体是杖。
  ⚠️ 但绽裂那段的注释（`:319-320`）承认它曾写错过一次（把同一个属性传两遍 = 恒定 ×1.00），
  **照抄时别把那个错误一起抄过来**。
- **正负不平衡的额外惩罚**：建议**先不加**，看 A 案跑一轮再定。

### 4.5 接入"梦境房间原料"的接口在哪 —— 就在 `piece` / `room` 那套

**答：接口已经通了，而且有三条通路。**

| 通路 | 现在的走法 | 情绪方块接入后 |
|---|---|---|
| **① 玩家自建组件** | 梦境里搭地台 → `/madnesstheory piece save <名字> [intensity]`（`MadnessCommands.java:558`、`savePiece` `:590`）→ `capturePad`（`DreamRoom.java:321`）→ `symbolOf`（`:336`）→ 写 `run/madnesstheory_pieces/<名字>.json`（`DreamPieces.SAVE_DIR`，`:51`） | **零改动** —— `symbolOf` 第 `:337-338` 行直接认这两个方块 |
| **② 生成时抽取与放置** | `DreamSession.enterDream`（`:84-132`）→ `DreamPieces.plan`（`:166-185`）→ `DreamRoom.build`（`:96`）→ `applyFace`（`:159`） | **零改动** —— `applyFace` 的 `case 'L'/'D'`（`:199-200`）直接产出这两个方块 |
| **③ 让心绪决定房间长什么样** | `progressOf`/`setProgress`（`DreamSession.java:398-404`）**目前只能靠命令改**（`DreamSession.java:34-37` 写明"进度现在不参与任何判定"） | **这是"特殊玩法"的真正接口** |

**③ 的具体落点（本方案最值得做的一段）**：
`DreamPieces.pick` 现在的选择依据**只有 `intensity` 与权重**（`:188-213`）。
可以让**玩家的心绪存储**参与权重：

```
pick(pool, progress, random)
  → 先按 intensity 窗口 WINDOW=0.3 硬筛（:191-194，不动）
  → 【新增】给每个候选算一个"心绪契合度"：
        组件里 L（明）的占比  vs  玩家正面心绪占总量的比例
        （正面总量可用 EmotionMoodStore.decodeTotals 拿到 HUD 用的那个数组，:145-158）
  → 契合度只在加权时乘一个系数，不改 intensity 硬筛
```

效果：**心绪里正面占多数 → 房间更可能抽到"明多暗少"的组件；反之亦然。**
这把"心绪存储"从一个**只进不出的计数器**，变成**会反过来塑造梦境世界的东西** ——
这正是"参与之后的特殊玩法"最自然的一种实现。

**代价与风险**：
- **建议不改 `pick` 签名**：由 `DreamSession.enterDream`（`:121-123`）在外面算好权重传进去更省。
- ⚠️ **种子确定性**：`DreamPieces.plan` 的注释写明"random 由调用方提供，
  这样同一个种子能完整复现'选组件 + 旋转'的全过程"（`:162-165`），
  而 `/madnesstheory room save|load` 正是靠它复现预设（`RoomPresets.java:28`）。
  **把玩家心绪混进权重，会让同一个种子在不同心绪下抽出不同房间 —— 预设复现失效。**
  建议：**只在真实入睡路径上用心绪加权；`room build/load/force` 命令路径保持纯种子**，
  并在 `room save` 的提示里说明这一点。

### 4.6 为什么这个方向比砖窑好

| | 砖窑（被否） | 熔炼（新方向） |
|---|---|---|
| 产出 | 一件**物品**（余烬砖） | 一批**建材方块** |
| 连到哪 | 只能再灌回法杖 —— **绕回自己** | 连到**梦境维度**（模组的主线舞台） |
| 是否新行为 | 不是（仪式流程一字不变，只是多捡一块） | **是**（多了一条"情绪 → 建材"的生产线） |
| 与其它材质例外同级吗 | 不同级（只是多收一点） | **同级**（灵魂/紫颂花/紫珀砖各有一个"别人做不到的事"，下界砖终于也有了） |
| 复用已有代码 | 要新物品 + 新组件 | **方块复用现成的两种，接口复用现成的一套** |

**一句话**：砖窑是"给下界砖多加一个抽屉"，熔炼是"给下界砖一个**下游产业**"。

### 4.7 两个必须一起改的实现细节

1. **`symbolOf` 是这条链的闸门**（`DreamRoom.java:336-343`）。
   它现在只认 5 个方块（`MOOD_LIGHT`/`MOOD_DARK`/三个 marker），**其它一律返回 `'.'`**。
   若"情绪方块"做成**任何新注册的方块**，玩家用它搭的房间
   `piece save` 会**静默地把它们读成空气**（`'.'` = 保持底色），存出来的是一张空白图 ——
   **而且不会报错**。→ 这直接决定 §4.2 的取舍：**要么复用这两个方块（A 案，零改动），
   要么必须同步扩 `symbolOf`**。没有第三条路。
2. **`EmotionStatueKind.initSources` 里紫水晶的归属**（`:304-306`，见 §3.4）。
   它同时影响 §3（洗炼基座）与 §4（外围种类选择），**两件事都动同一个枚举**，
   建议**放在同一轮改**，不要分两次动 `EmotionStatueKind`。

## 5　第 7 条"得修"—— trait 下沉到材质级的修法

### 5.1 现状（本次新核对）

- `EmotionStatueKind` 的 `trait` 是**构造参数的第 6 项**，每 kind 一个（`EmotionStatueKind.java:90-99`）。
- `StatueMaterial` **也有 `kind()`**（`StatueMaterial.java:198`），110 条材质各自指向一个 kind；
  它**没有自己的 trait 字段**（字段集见 `:174-186`：id / kind / sideTexture / topTexture）。
- 所以"材质级差异"在数据上**不存在**，现在只有"长相"不同。

### 5.2 真下沉要动哪些地方

| 要改 | 内容 | 量级 |
|---|---|---|
| `StatueMaterial` | 加 `trait` 字段 + 构造参数 | **110 条**（脚本生成则重跑；手改必错） |
| 所有取 trait 的地方 | 现在一律 `kind.trait()`，要改成"材质优先、回落 kind" | `RitualEffects.java:182/183/324`、`EmotionStatueItem.java:63`、`BiomeMoodHintDebug.java:208-221`、`MadnessCommands.java:223` |
| 仪式路径 | `Result.outerKind()` **只有 kind、没有材质**；`tryBurst` 的注释明确写了"现有数据模型里'材质'就是 `EmotionStatueKind`，没有更细的一级"（`RitualStructure.java:153-155`） | **要扩 `Result`**，牵连 `match` 三个分支 + `dbgRitual` 输出 |
| 展示 | tooltip（`EmotionStatueItem.java:59-80`）与 `/emotion statue` 输出 | 中 |

**结论：真下沉是"大"工程（同时动 110 条材质 + 判定链），而目前真正需要材质级的只有紫颂花一个。收益不成比例。**

### 5.3 我建议的省法（推荐）

**保留 kind 级 trait 不动，只在确实需要材质级的那几条特性上做局部特判。**
理由是**数据已经在手上**：

- **法杖侧**：`EmotionPayload.materialId()`（`EmotionPayload.java:45`，`GuideBookItem.java:346` 写入）
  —— 判紫水晶/紫颂花**不需要任何新字段**。
- **环境侧（雕像方块）**：`state.getValue(EmotionStatueBlock.MATERIAL)`（`EmotionStatueBlock.java:59-61`）。

写成一个**纯函数**即可，不牵动枚举结构：

```
// 建议放在 StatueTrait 或一个新的工具类里
public static boolean isMaterialOf(EmotionPayload p, EmotionStatueKind want) {
    StatueMaterial m = StatueMaterial.byIdOrNull(p.materialId());
    return m != null ? m.kind() == want
                     : EmotionStatueKind.byId(p.kindId()) == want;
}
```

**额外好处**：它天然兼容**旧法杖** —— 旧载荷没有 `material` 字段，`EmotionPayload` 的 codec
用 `optionalFieldOf("material", "")`（`:44-45`）读成空串，于是回落到 kind 判据。
**这正是"下沉到材质级"想要的效果，却不用动 110 条数据。**

**建议**：把"要不要真下沉"推迟到出现**第二个**需要材质级功能的特性时再决定；
现在用局部判据，把 `StatueTrait` 留作"kind 级的粗粒度开关"。

## 6　第 8 条（`ritualPayload` 不序列化）的具体修法

### 6.1 现状（复核确认）

`EmotionStatueBlockEntity.writeContained`（`:549-557`）只写两样：

```java
output.putInt("ritualTicks", this.ritualTicks);
if (!this.contained.isEmpty()) output.store(KEY_ITEM, ItemStack.CODEC, this.contained);
```

而 `ritualPayload`（`:94-95`，类型 `EmotionPayload`）**不在里面**。
后果：升华/沉坠的注入是**600 刻后才落地**（`RitualEffects.java:202-216`），
这 30 秒里**区块卸载或退出游戏 → 待结算的注入永久丢失**，
而记录**已经**在 `:220-221` 被打上已消耗标记（且 `cancelRitual` 明确不退还，`:175-176`）。

### 6.2 修法

**① 要序列化哪些字段**
- **必须**：`ritualPayload`（有现成 Codec：`EmotionPayload.CODEC`，`EmotionPayload.java:33-46`）。
- **建议一并**：`ritualKind`（`:81`）与 `ritualDuration`（`:83`）。
  它们现在也没存 —— 读回来恒为 `AWAKENING` 与 `RITUAL_TICKS`（140），
  导致 `serverTick` 里 `if (be.ritualKind != RitualKind.AWAKENING)`（`:312`）**判错分支**：
  一场升华仪式在存档往返后会走"唤醒仪式"的粒子逻辑。
- **建议一并**：`ritualOuter`（`:85`）—— 因为 `cancelRitualOwningThisPosition`（`:240-258`）
  靠它判断"本坐标是不是某场仪式的外围"，不存的话"拆掉外围雕像应当打断"这条语义会失效。
- **不必存**：`ritualPlayer`（玩家可能已离线）、`ritualColor`（`:88-93` 已注明不再使用）。

**② `writeContained` 与 `getUpdateTag` 是否都要改 —— 建议只改一半**
理由来自这个类自己的注释（`:470-475`）：`getUpdateTag` 是**同步给客户端**，`saveAdditional` 是**存档**。

- **`saveAdditional` 侧：必须加** `ritualPayload`（否则就是现在的丢注入 bug）。
- **`getUpdateTag` 侧：不要加**。因为：
  1. 客户端**不需要**知道待结算载荷 —— 台座上那根杖此刻的数值**故意**还是旧值
     （`:202-204` 解释了为什么不能立刻写入：动画期间状态不能自相矛盾）。
     同步过去会让**中途加入的玩家**看到"法杖已经是新数值"，与房主看到的动画不一致。
  2. 同步包越小越好（`EmotionPayload` 有 8 个字段，含两个 String）。

→ **实现**：把 `writeContained` 拆成两个入口（或加 `boolean forClient` 参数）：

```
writeContained(output)   → 客户端也要的（ritualTicks + contained）—— 维持原样
writeSaved(output)       → 存档专属（调 writeContained，再加 ritualPayload / ritualKind / duration / outer）
```

⚠️ 类注释说"两边的字段必须保持一致"（`:474`）—— **那条规矩的用意是"防止漏改"，
不是"两边字段必须相同"**。这次是**有意分叉**，所以要把注释一并改掉，
否则下一个人会以为这是漏改，反而把 `ritualPayload` 也同步给客户端。

**③ 旧存档兼容**

     ——材料 id 已经存在载荷里（`EmotionPayload.java:45` 的 `material` 字段），
     下界砖家族的 4 个方块 id 见 `EmotionStatueKind.java:288-289`。
   - **落法 B**：给下界砖单独拆一个 `EmotionStatueKind`。**不推荐**：会动 19→20，
     牵连 `StatueMaterial` 生成、书页清单、命令输出，成本高且收益相同。
   **本文档给出的下界砖方案均按落法 A 写实现落点。**
3. 每次改 `StatueTrait` 的 switch 都要注意：`positiveMultiplier` / `negativeMultiplier`
   是 `default -> 1.00`，**漏写 case 不报错、只是静默拿 1.00**（`StatueTrait.java:89-90` 自己写了这条教训）。

## 点子 1　回响（`ECHO`）—— 释放的"形状"由杖的材质决定

**挂给谁**：新种类，不新增方块。给已有的 **SCULK / ABYSSAL / DRIPSTONE / CORROSION / TRIAL** 这 5 个
「第二批」种类各派一种释放形态（它们现在除了乘数之外一无所有，是最空的一批）。

**效果**：挥杖时的作用形态随杖的种类变化 ——
- 潜声石像 → 作用域内所有生物**互相**传导（对 A 施加的同时，A 附近的 B 也吃到一半）
- 深海石像 → 作用域改为**沿视线一条直线**（穿一条走廊），半径换成长度
- 石笋石像 → 作用域变成**自己脚下起跳的垂直柱**（向上/向下各 N 格）
- 蚀痕石像 → 效果**贴上目标一段时间**（离开范围后仍然延续一次）
- 试炼石像 → 作用域随**在场敌对生物数量**放大

**它创造了什么玩法**：玩家选杖不再只看数值，而是看**战场形状**。
窄走廊用深海、刷怪笼房间用潜声、下矿竖井用石笋。
这让"去哪个群系记录情绪"这件事第一次和"我要打什么"挂钩 ——
现在这两件事是**完全脱钩**的（`EmotionStaffItem.java:136-153` 只有"半径"一种形态）。

**实现落点**：
- `EmotionStaffItem.java:135-153`：把 `releaseAround()` 拆成按 kind 分派的一组形态函数，
  入参已有 `EmotionPayload p`，`p.kindId()` 直接可取到种类。
- `EmotionStaffItem.java:155-170`：`applyEffect` 增加一个"延迟一次"的参数（蚀痕用）。
- 无需新状态、无需新包。

**平衡风险**：低。作用域变化影响的是**打击面**而不是**强度**，
而强度公式 `EmotionStaffItem.java:157` 的 `duration = clamp(power × 20, 20, 600)` 完全不动。
唯一要注意的是深海"直线"可能被用来隔墙打人 —— `findTarget` 已经要求 `hasLineOfSight`
（`EmotionStaffItem.java:113`），复用同一个判定即可。

**实现难度**：**小**。纯服务端分派，无新数据结构。

## 点子 2　同调（`ATTUNED`）—— 雕像**群**的"成套"加成

**挂给谁**：不挂给某一种类，挂成一条**通用规则**，但由 trait 开关（首发给 COBBLE / NETHER_BRICK / END_ROCK 这些"砖石"类）。

**效果**：以中心雕像为原点、半径 8 格内，**每有一尊与中心【同一种类】的雕像**（不论朝哪、不论台座里有没有东西），
中心那尊的属性偏好额外 `×(1 + 0.05 × n)`，`n` 上限 8（即最多 ×1.40）。
玩家的雕像**收藏**第一次有了数值意义。

**它创造了什么玩法**：把"雕像"从功能性单件变成**建筑/收藏**。
玩家会开始在基地里摆一整面下界砖雕像墙，而不是把雕像当一次性耗材。
同时它天然奖励"不要到处乱摆"——集中摆放才有收益，与 `RitualStructure` 要求的
"外围必须同类、必须紧邻"形成同一种审美（"仪式场"），强化了模组的空间语言。

**实现落点**：
- `RitualEffects.inject()` 里 `double loss = ...` 那一行**之前**（`RitualEffects.java:186`）插一层：
  扫中心周围 8 格内的 `EmotionStatueBlock`，数同类。
- `RitualEffects.burst()` 同理，插在 `RitualEffects.java:327` 的 `boosted` 计算之前。
- 需要一个 `RitualStructure` 上的静态工具方法（如 `countSameKindNear(level, center, kind, radius)`），
  复用 `RitualStructure.statueKind(...)`（`RitualStructure.java:240-245`）。
- **性能注意**：半径 8 = 17×17×3 ≈ 867 个方块状态读取，**只在仪式触发那一刻跑一次**，
  可以接受；但**不要**放进每刻的 `serverTick`。

**平衡风险**：中。它直接乘在偏好层上，而偏好层是**平方**的（外围 × 中心），
所以 +40 % 的群加成在上述公式里会变成接近 +96 %（1.4²）的实际增幅。
建议**只在中心那一层加**（`×1.4` 而不是 `×1.96`），或者把系数降到 0.03/尊、上限 0.24。
另外要防"用 9 尊泥土雕像凑数"——泥土属性是自然，对非自然记录本来就 ×1.00，所以蹭不到，
这一点是自洽的。

**实现难度**：**小～中**（要一个邻域扫描工具；无新状态、无新包）。

## 点子 3　属性即偏食（`PALATE`）—— 雕像属性改写"哪一半被抛弃"

**挂给谁**：通用规则，**下界四件套**为默认持有者（见第三节，这条与下界砖方案 B 强相关）。

**效果**：升华时本该"只取正面、负面彻底消失"（`RitualEffects.java:138-139`）。
拥有本特性的雕像，把"抛弃"改成"**吃干榨净**"：
被抛弃的那一半 `(1 - ratio)` 不再蒸发，而是按 **15 %** 的比例**折进本次注入量**。
**极性方向不变**（升华仍然只产出正面），变大的只是点数。
所以极端记录（`ratio` 接近 0 或 1）几乎无感，
而中间态记录（`ratio ≈ 0.5`）能多榨出约 7.5 %。

**它创造了什么玩法**：让"参半记录"（`ratio ≈ 0.5`，现在两头都不划算、最鸡肋的一类）
第一次有额外价值，从而把玩家的行为从"只留极端记录、其它随手烧掉"
推向"**中间态也值得攒**"。
配合 `Config.GROUP_DEFAULT_RATIOS`（`Config.java:194-198`）里 `haunted/void` 的 0.00-0.25 区间，
玩家会为了"让每条记录都不浪费"而愿意在普通群系多记几条 —— 这是目前最缺的"低档记录的价值"。

**实现落点**：
- `RitualEffects.inject()`：`int total = (int) Math.round(amount * share);`（`RitualEffects.java:139`）
  这一行之后加分支：若中心 kind 的 trait 有此特性，
  `total = total + round(amount × (1 - share) × 0.15)`。
- **建议只让"中心雕像"吃这个特性**（外围四尊已经是纯粹的效率件），
  否则外围同类 ×4 又要纠结是不是乘四次方（`RitualEffects.java:174-178` 的注释已经踩过这个坑）。

**平衡风险**：中低。
`ratio = 0.50` 时 `total` 从 16 变 `16 + 32×0.5×0.15 ≈ 18`（+15 %）；
`ratio = 1.00` 或 `0.00` 时**完全无变化**（被抛弃份额为 0）。
所以它**天然只作用在中间态记录上**，不会推高现有极值。
**真正的风险是与点子 2（同调，群加成最多 ×1.40）叠加** —— 若两条挂到同一种类，
会一起把注入顶向 336 点以上，冲爆"心绪两次才满"的节奏设计
（`RitualEffects.java:315` 的 `×1.5` 转换比与 `EmotionMoodStore.java:34` 的 150 是配套的）。
**建议**：两条**不要挂在同一个种类上**。

**实现难度**：**小**（纯算术分支）。

## 点子 4　共鸣消耗（`RESONANT`）—— 用心绪"喂"仪式

**挂给谁**：新种类，建议绑 **紫水晶块 / 紫水晶簇 / 重生锚**（发光、结晶感的方块家族，目前完全未被使用）。

**效果**：举行升华/沉坠时，若玩家心绪存储里**某一种心绪 ≥ 40 点**，
可以（在右键时潜行 = 主动选择）投入 40 点该心绪，使本次注入 **直接按该心绪的属性重算属性层**，
并且额外 `×1.35`。投入的心绪从存储扣掉。

**它创造了什么玩法**：**这是把第二阶段的"心绪"接回第一阶段"仪式"的唯一一条线**，
而这条线现在是断的 —— 心绪目前只有一个出口（HUD 显示 + `burst()` 的产物），
**没有任何消耗途径**（全仓 `EmotionMoodStore.take(...)` 只在 `MadnessCommands` 的调试指令里被调用，
"未核对是否还有其它调用点"，但至少仪式路径上没有）。
玩家会形成"**攒心绪 → 换仪式效率 → 攒更快**"的正循环，
并且第一次需要**在两个池子之间做取舍**（心绪要不要留着以后用体力类能力）。

**实现落点**：
- `GuideBookItem.useOn()`（`GuideBookItem.java:268-279`）是唯一的仪式入口：
  这里读出 `player.isShiftKeyDown()`，把"投入哪种心绪"塞进 `RitualStructure.Result`
  （或做成 `perform` 的额外参数）。
- 扣款：`EmotionMoodStore.take(data, mood, attrId, 40)`（`EmotionMoodStore.java:108`）+ `syncTo`。
- 加成：`RitualEffects.inject()` 的 `pref` 末尾（`RitualEffects.java:184` 之后）。
- ⚠️ 注意 `RitualStructure.match()` 的签名会被牵连（多一个 `java.util.function.Consumer<String> why`
  overload 已经存在，可以逐个加重载，不必拆掉现有调用）。

**平衡风险**：中。真正的风险不是数值，而是**"心绪被消耗后能不能回来"**——
`EmotionMoodStore` 没有回收机制，一旦某类心绪被换成效率，玩家可能**永久失去做某件事的资格**
（如果将来心绪能力是持久解锁）。**建议**：把投入量定为"**只扣超出 40 的那部分**"或做成
"标记占用而非扣除"，等心绪的正式消耗语义定了再表态。

**实现难度**：**中**（要动 `RitualStructure.Result` 的字段与 `match` 的签名，牵连 3～4 个调用点）。

## 点子 5　酒意 / 陈化（`AGED`）—— 记录"放久了"会变浓也会变脏

**挂给谁**：新种类，建议绑 **木桶 / 酿造台 / 炼药锅 / 堆肥桶**（"容器 + 时间"的意象，未被使用）。

**效果**：石碑类雕像在**雕像自身**上累计"陈化度"（每 Minecraft 日 +1，上限 +3）。
举行仪式时，队首那条记录若**已经被记录过超过 3 个 MC 日**（用现有 `EmotionRecords` 的时间？
——**代码里没有记录时间戳，未核对可行**），本次 `total` `×(1 + 0.25 × 陈化度)`，
但同时**心绪的属性标签被清空**（走 `EmotionMoodStore` 里 `attrId = ""` 那条路子，
`EmotionMoodStore.java:55-63` 明确支持无标签条目）。

**它创造了什么玩法**：制造了"**囤 vs 用**"的经典取舍，而且是**有代价的囤**：
浓了，但失去属性加成（`RitualEffects.java:181-184` 的属性层直接跳过）。
玩家会刻意"攒一批记录放几天"，也会为了"等它陈化"而不敢立刻消耗。
配合 `hintCooldownMin/MaxSeconds`（`Config.java:32-39`，默认 20～600 秒）的长冷却，
"囤"是有意义的，因为**记录本身就很慢**。

**实现落点**：
- **前置障碍**：`EmotionRecords` 的存档段（`EmotionRecords.java:104-107` 的 `segments(...)`）
  **没有时间字段**。要落这条必须先往分段列表**再追加一段**（文档 §3.4 明确说分段是向后扩展的，
  旧数据段数不够读出来是空串 → 天然兼容）。这一段需要作者先拍板"时间戳要不要进存档"。
- 陈化度若要存在雕像上，要给 `EmotionStatueBlockEntity` 加字段，
  且**必须同时改 `writeContained`（`EmotionStatueBlockEntity.java:549`）与 `getUpdateTag`**——
  该类注释（`:470-475`）明确写了"加字段时两处都要改"。

**平衡风险**：中低。因为它自带惩罚（丢属性标签），
在属性层能吃到 ×2.00 的组合里，丢标签的损失远大于 +25 % 的收益，所以**不会被无脑滥用**。
真正的风险是**存档兼容**：这是全文档里唯一会动 `EmotionRecords` 存档格式的点子，
而那份文档 §3.4 与 `癫狂构想-第二阶段实施方案.txt` 的 §9（卸载与存档兼容）
都把它列为高危区，必须单独一轮做。

**实现难度**：**大**（新持久字段 ×2 + 存档格式扩展 + 客户端表现）。

## 点子 6　跨维度回声（`REMOTE`）—— 末地雕像的"末影箱"式联动

**挂给谁**：**紫珀砖（PURPUR）** —— 它现在的 `sharedStorage()` 是空功能（见 §1.3③），
这条是它的**可落地替代品**，保留了"末影箱式共享"的**设计意图**，但换了一个能实现的机制。

**效果**：同一玩家在**任意维度**的两尊紫珀砖雕像**互相绑定**（用方块实体存一个共享 UUID，
或更省事：用"玩家 UUID + 雕像坐标"做成固定配对）。在 A 处举行升华/沉坠，
法杖里注入的情绪会**同时镜像到 B 处台座上的法杖**（B 处的杖必须也是紫珀砖材质、且含量不冲突）。

**它创造了什么玩法**：**这是目前唯一的"跨维度物流"**，直接改变玩家的基地布局：
在主世界基地摆一尊紫珀砖雕像、在下界矿场摆一尊，
下界记到的负面情绪可以**就地仪式、基地提货**。
它把"要不要跑回家"这个日常摩擦变成了可投资的基建。

**实现落点**：
- 绑定关系：`EmotionStatueBlockEntity` 新增可选的"配对坐标 + 维度"字段
  （**又是那个坑**：`writeContained` `:549` 与 `getUpdateTag` `:477` 都要改）。
- 镜像写入：`EmotionStatueBlockEntity.finishOuterRitual()`（`:672-688`）
  是注入真正落地的那一刻，**这是唯一的写入点**，在这里加镜像最干净。
- 目前未见任何"雕像之间互相寻找"的先例，需要新写一个跨维度坐标查找
  （`level.getServer().getLevel(dim)` + `getBlockEntity`）。

**平衡风险**：中。它**不增加任何数值**，纯粹是物流便利，所以不会被"滥用"。
风险在两点：① 目标区块**未加载**时镜像会静默失败 → 必须给玩家明确反馈（不能静默，
   本项目已经吃过"静默失败被误判成功能坏了"的亏，见 `RitualEffects.java:141-146` 的注释）；
② 若允许多尊互联，会变成"一根杖全网同步"的怪东西，**必须限制为 1 对 1**。

**实现难度**：**中～大**（要新状态 + 跨维度查找 + 未加载处理）。

## 点子 7　补料（`SUBSTITUTE`）—— 结构不完美时，"牺牲"一尊雕像来补

**挂给谁**：新种类，建议绑 **砂轮 / 铁砧 / 锻造台 / 高炉**（"加工 / 修补"意象，未被使用）。

**效果**：升华/沉坠要求外围四尊齐备且同类（`RitualStructure.java:164-201`）。
拥有本特性的雕像放在**中心**时，允许**缺一尊**外围，但代价是：
被缺的那一尊所代表的效率按 **×0.60** 计（而不是 ×0.90），并且**本次仪式的记录消耗翻倍**（烧两条）。

**它创造了什么玩法**：**这是"降低门槛"型的功能，专门解决新玩家的第一道墙** ——
凑四尊同类雕像对刚入门的玩家是真实的门槛（尤其是"同一种类"这个要求，
`RitualStructure.java:185-188` 会明确拒绝混类）。
有了补料，玩家可以"三尊 + 一尊补料"先跑起来，付双倍记录费。
它把"结构判定失败"从**硬墙**变成**可议价的成本**，显著改善前 2 小时的体验。

**实现落点**：
- `RitualStructure.tryInward()`（`:164`）：`if (!(... instanceof EmotionStatueBlock))` 那一处（`:172`）
  返回 null → 改成"记一个缺口，继续扫描"，最后 `Result` 里多带一个 `shortfall` 字段。
- `RitualEffects.inject()`：`r.injectionLoss()`（`:186`）用一个按缺口打折的值；
  记录消耗在 `:220-221`，改成循环两次（注意第二条可能不存在 → 要兜底）。

**平衡风险**：中。风险集中在"双倍记录消耗"是否真的构成代价 ——
现在一条记录很慢（`Config.HINT_COOLDOWN_MIN_SECONDS = 20`，`HINT_RECORD_WINDOW_SECONDS = 60`），
所以是的，代价是真的。但**要防止"补料被当成常态最优解"**：
如果 4 尊齐全的收益是 `0.90²`，缺一是 `0.60 × 0.90 = 0.54`，差 33 %，
换一条记录……**这条账玩家可能算得过来"其实差不多"**。建议把缺口折扣压到 **×0.50**。

**实现难度**：**中**（要改 `RitualStructure.Result` 的结构，牵连 `match` 三个分支与调试指令输出）。

## 点子 8　雕像即基站（`BEACON`）—— 环境提示的速度升级

**挂给谁**：新种类，建议绑 **信标 / 潮涌核心 / 海晶灯 / 末地烛**（"信号 / 扩散"意象）。

**效果**：以该雕像为圆心、半径 16 格内，玩家的**环境提示冷却减半**
（`hintCooldownMin/MaxSeconds`，`Config.java:32-39`），
并且 `Config.HINT_RECORD_WINDOW_SECONDS`（`Config.java:43`，默认 60 秒）**翻倍**到 120 秒
（记录窗口更长 = 更不容易错过"已记录"的时机，这个字段配合 `activeRecorded` 使用，
见实现设计文档 §1.3）。

**它创造了什么玩法**：**这是唯一一条直接作用于"第一阶段最慢那一环"的点子。**
现在玩家的实际体验是"到处走、等提示、等记录"，而记录是升级的唯一燃油。
一尊信标雕像能把"效率"这件事从**运气**（走到哪个群系）变成**基建**
（把雕像摆在自己常待的地方，或者干脆摆在群系交界处）。
它还会催生一个真实的位置选择问题：**摆在基地（常待）还是摆在群系边缘（产出多）？**

**实现落点**：
- `BiomeMoodHint`（负责冷却与提示触发，见实现设计文档 §1）——
  **该类在本次通读中没有逐行读，标「未核对」**。
  机制上需要在它每次计算冷却时，做一次"附近有没有 BEACON 雕像"的查询。
- 查询建议**缓存**：不要每 tick 扫，用"玩家位置变化 > 4 格才重算"或者用
  `MoodAttachments` 里存一个带过期时间的缓存值。

**平衡风险**：**高**。这是本文档里最可能"失控"的一条，因为它作用在**系统的上游**：
记录快了 → 一切都快。要控住必须**限幅**：
半径不能大（16 格已经不小）、加成不能叠（多尊不叠，取最高）、
且**明确不动 `hintsNeededForDream`**（`Config.java:50-53`，梦境门槛不能一起降，
否则整条主线都被压缩）。
另外 `EmotionRecords.java` 与 `BiomeMoodHint` 的交互细节**未核对**，
实现前必须先读那两处确认"冷却到底在哪个方法里算"。

**实现难度**：**中**（逻辑简单，但要摸清 `BiomeMoodHint` 的调用时机并做缓存）。

## 点子 9　回收（`SALVAGE`）—— 被抛弃的那一半，回来一点

**挂给谁**：新种类，建议绑 **漏斗 / 投掷器 / 熔炉 / 烟熏炉**（"回收 / 再加工"意象）。

**效果**：升华沉坠时本该"彻底消失"的那一半（`RitualEffects.java:138-139`，
作者在第二阶段方案 §11 Q6 明确定为「彻底消失」），
在中心是这样的雕像时，**10 %** 以**当前法杖已有的极性**折回注入。

**它创造了什么玩法**：**与点子 3（偏食）方向相反的一条：偏食奖励极端，回收奖励中庸。**
回收让"参半记录"（ratio ≈ 0.5，两头都不划算）第一次有价值 ——
现在 `ratio = 0.5` 的记录无论升华还是沉坠都只能取一半，是最"鸡肋"的一类。
它会鼓励玩家**不要挑食**，把路上随手记的普通记录也拿去烧。

**实现落点**：
- 与点子 3 同一处（`RitualEffects.java:139` 之后），但**用另一个 trait 名**，
  两者互斥（同一次仪式只能吃一条）。
- **不要**做成"存进法杖"（那会让法杖的极性变混，`ratio` 是单值的，
  `RitualEffects.java:200` 会覆盖成 1.0 或 0.0 —— 与"混装"根本冲突）。

**平衡风险**：低。10 % 的回收率对应的期望增益很小（`ratio=0.5` 时 +5 %），
且它**只作用在参半记录上**（因为极端记录的丢弃份额本来就接近 0，回收不到东西）。
所以它天然是"新手友好 / 老手用不上"的良性特性 —— 这在一个已经有
"紫颂花断层"（见《倍率总表与意见》§9.1 问题 1，2.56 倍断层）的体系里，是可取的。

**实现难度**：**小**。

## 点子 10　延时绽裂（`DELAYED`）—— 把"零时长"的绽裂变成可布置的陷阱

**挂给谁**：新种类，建议绑 **TNT / 侦测器 / 标靶 / 红石灯**（"触发 / 延时"意象）。

**效果**：以这样的雕像为**外围**时，绽裂的结算**延后 200 刻（10 秒）**，
并且在延迟期间**持续向外扩散染色粒子**（颜色取 `pool` 里心绪的配色，
`RitualEffects.java:368-373` 已有现成的实现可以复用）。
若延迟期间玩家离开半径 16 格，绽裂**取消**（法杖不清空、心绪不发）。

**它创造了什么玩法**：现在的绽裂是**立即结算、零成本、零风险**的
（`RitualEffects.java:278` 的注释明确写了"绽裂没有动画时长，是即时结算的"，
《倍率总表与意见》§9.4 也把它列为失衡点）。
加了延时之后，绽裂第一次有了**"表演性"与"风险"**：
玩家可以把缀满情绪的法杖留在绽裂台上，10 秒里跑开去看效果，或者
**把绽裂台当陷阱**——引怪过来，在 10 秒里让扩散的粒子把怪堆在范围内
（如果作者愿意让绽裂对范围内的生物也有微弱效果，那就是一个完整的"爆裂陷阱"）。

**实现落点**：
- `RitualEffects.burst()`（`:278`）现在是同步的，需要改成
  "算好 → 交给 `EmotionStatueBlockEntity` 延时执行"。
  **`EmotionStatueBlockEntity` 已经有现成的延时框架**：
  `ritualTicks` / `ritualDuration` / `startOuterRitual` / `serverTick` 的
  `if (be.ritualTicks <= 0) finishOuterRitual(...)`（`:319-321`）—— **照抄这套即可**。
- ⚠️ `RitualKind` 枚举（`:79`）要加 `BURST`，`serverTick` 里的
  `if (be.ritualKind != RitualKind.AWAKENING)`（`:312`）分支要相应处理。
- ⚠️ **打断路径必须接上**：`cancelRitual`（`:171`）已经被 `setRemoved`（`:223`）
  和 `setContained`（`:447`）调用，新仪式**自动继承**打断保护 —— 这是本项目少见的
  "基础设施已经铺好、可以直接接"的位置，**成本远低于看上去的样子**。

**平衡风险**：低。它**不改变任何数值**，只改变时序，而时序风险由玩家自己承担。
唯一要小心的是"延迟期间服务器重启/区块卸载"——`setRemoved` 已经处理（卸载就当没发生），
符合第二阶段方案 §9 的兼容要求。

**实现难度**：**中**（框架现成，但要动 `RitualKind` 枚举与 `serverTick` 的分支，
且 `saveAdditional` 目前**只存了 `ritualTicks`，没存 `ritualPayload`**
—— `EmotionStatueBlockEntity.java:549-557` 只写了 `ritualTicks` 和 `contained`。
**这意味着现在升华/沉坠仪式中途退出游戏，待结算的载荷会丢**。
这是一条**既有隐患**，做点子 10 时必须一起处理。）

## 点子 11　交换台（`BARTER`）—— 雕像上的记录"换手"

**挂给谁**：新种类，建议绑 **讲台 / 书柜 / 制图台 / 附魔台**（"书 / 交换"意象）。

**效果**：把**指南书的记录**变成**可搬运的实体**。
对这样的雕像右键，可以取出一片"情绪残页"物品（带 `ModComponents` 数据组件，
内容是某一条记录的 id/属性/档位）；残页可以交给**另一尊**同类雕像放回书里。

**它创造了什么玩法**：**这直接接上了文档 §10.5 与第二阶段方案 §4 里悬而未决的"撕页"设计。**
作者已经定了"撕页改成合成：书 + 剪刀 → 纸"（第二阶段方案 §4），
但那个方案的问题是"纸"是个**没有内容**的材料。
**残页**是同一个交互的**更有内容**的版本：撕下来的不是空白纸，是**真的那一条记录**。
副产品是：
- 记录的**顺序**第一次可以被玩家改变（现在消耗严格按"最先未消耗"，
  `RitualEffects.java:242-249` 的 `firstUnconsumedIndex`）——
  这直接解决了 `StatueTrait.java:24-27` 注释里记的那个**死锁教训**
  （"想用空无雕像时必须先消耗掉前面所有其它属性的记录"）。
- 玩家之间可以**交易具体记录**。

**实现落点**：
- 新物品 + 新数据组件（照 `ModComponents.STATUE_KIND` 的写法，`ModComponents.java:38-41`，
  **必须同时给 `persistent(CODEC)` 与 `networkSynchronized(STREAM)`**，
  该文件注释 `:12-17` 专门警告过只给一个的后果）。
- 记录的搬运：`MoodAttachments.MoodData.recorded` 是 `List<String>`，
  单条就是 `EmotionRecords` 的存档行，**天然可以整行搬走**。
- 交换台逻辑挂在 `GuideBookItem.useOn` 旁边（或新物品的 `useOn`）。
- ⚠️ **同步刷新的雷**：任何改动 `recorded` 的地方**都必须同时**
  `player.setData(MoodAttachments.RECORD_BOOK_TEXT, EmotionRecords.joinForSync(...))`
  （`RitualEffects.java:222`、`GuideBookItem.java:330` 都是这么做的，
  实现设计文档 §7 的表最后一行专门警告过漏刷新）。

**平衡风险**：中。它**不给任何数值**，所以不会失控；但它是**操作记录顺序**的能力，
而"顺序"现在是这套系统的**唯一约束**（也是死锁的来源）。
一旦顺序可改，`RitualEffects.java:148-166` 那个"total ≤ 0 就烧掉队首"的失败分支
会变得更常被触发（玩家可以把不想要的记录推到队首去烧）。
**这谈不上坏**，但作者要意识到这是**故意打开的一个口子**。

**实现难度**：**大**（新物品 + 新组件 + 新交互 + 记录搬移 + 同步刷新，
是本文档里工程量最大的一条，但也是**设计价值最高**的一条）。

这正是作者说它"最平"的意思。所以下面三个候选**都不以"加强数值"为目标**，

## 方案 A（推荐）　砖窑：把被抛弃的那一半"烧成砖"

**建议 trait 名**：`NETHER_BRICK_KILN`（若按 §1.5 落法 A 实现，则不必新增枚举值）

### 效果

下界砖雕像（**作为中心**）举行**升华或沉坠**时，
本该"彻底消失"的那一半情绪（`RitualEffects.java:138-139`）不再凭空蒸发，
而是**凝成一块实体**：

- 一块「**余烬砖**」（新物品）出现在中心雕像的台座旁边（掉落在地上，或塞进相邻的容器）
- 每块余烬砖记录 **极性 + 属性 + 点数**（点数 = `round(被抛弃份额 × 0.25)`，
  即 25 % 回收率，且**上限 32 点**）
- 玩家手持余烬砖右键**任意雕像的台座**，可以把这 25 % **不加损耗地**灌进台座上的法杖
  （不触发仪式、不耗时、不消耗记录）

### 它创造了什么玩法（最重要的一节）

1. **下界砖变成了"加工站"而不是"容器"**：玩家会**专门把下界砖雕像摆到仪式场**，
   而不是随便找个石头当中心。这是下界砖第一次有"摆在哪"的问题。
2. **诞生了一条新的物品流**：余烬砖是**可携带、可堆叠、可交易**的情绪载体 ——
   目前模组里情绪的**唯一**载体是法杖（`EmotionPayload` 挂在 `ModComponents.EMOTION` 上），
   所以"带一点情绪回家"这件事现在**做不到**（法杖会整根占用，且释放即清空）。
   余烬砖补上了这个空缺。
3. **它给了"参半记录"一个归宿**：`ratio ≈ 0.5` 的记录无论升华还是沉坠都只能取一半，
   是最鸡肋的一类。有了砖窑，另一半不再白扔 —— **每次仪式都不亏**，
   这会显著降低新手的挫败感（现在"烧掉一条记录拿 1 点"是真的会让人以为机制坏了，
   见 `RitualEffects.java:148-166` 那条失败分支的血泪注释）。
4. **为多玩家互动开门**：余烬砖是**第一件可以给别人的情绪**。

### 实现落点

- **触发点**：`RitualEffects.inject()`，即 `int total = (int) Math.round(amount * share);`
  （`RitualEffects.java:139`）之后。此处 `st`（`EmotionRecords.Stored`）与
  `amount` / `share` / `positive` 全都在手，**算"被抛弃的那一半"不需要任何额外信息**。
- **判断"中心是不是下界砖"**：
  按 §1.5 落法 A，用 `level.getBlockState(center).getValue(EmotionStatueBlock.MATERIAL).id()`
  做前缀判断（4 个 id 见 `EmotionStatueKind.java:288-289`），
  或更严格地做成一张 `Set<String>` 白名单。
  **这样不必新增 `EmotionStatueKind` 枚举值**，不牵连 `StatueMaterial`、书页清单、命令输出。
- **"延后到仪式结束"这一条要遵守**：现在的注入是**600 刻后才落地**的
  （`RitualEffects.java:202-216`：载荷存进方块实体，`finishOuterRitual`
  `EmotionStatueBlockEntity.java:672-688` 才真写入）。
  余烬砖**必须也在那一刻生成**，否则动画期间地上就多出一块砖，观感自相矛盾。
  → 落点是 `finishOuterRitual()`，需要给方块实体多存一个"待产出的余烬砖参数"
  （与现有 `ritualPayload` 同生命周期）。
- **⚠️ 立刻要修的既有隐患**：`EmotionStatueBlockEntity.writeContained()`（`:549-557`）
  **没有存 `ritualPayload`**，所以现在**升华/沉坠仪式中途退出游戏，待结算的注入会丢**。
  做本方案会往这里再加一个字段，**必须顺手把 `ritualPayload` 一起序列化**。
- **余烬砖物品**：新物品 + 新数据组件。照 `ModComponents.STATUE_KIND`（`ModComponents.java:38-41`）
  写，**`persistent(CODEC)` 与 `networkSynchronized(STREAM)` 两个都必须给**（该文件 `:12-17` 的警告）。
- **注入余烬砖**：读法杖载荷 → `payload.amount() + 砖点数` → 写回。
  ⚠️ **不要**改 `ratio`（`EmotionPayload.java:31` 是单值，改了就破坏"极性纯粹"这个绽裂的前提）。

### 平衡风险

- **会不会绕过主体玩法？** 会一点，但已限幅：
  25 % 回收 + 上限 32 点，意味着**一条 32 点记录最多回收 8 点**（32 × 0.25 × 被抛弃份额）。
  它**远低于**正常仪式的注入量（最高 336 点），所以没人会为了余烬砖去刷仪式。
- **会不会与绽裂叠加失控？** 这是**真正要盯的点**：余烬砖是"免仪式把点数灌进杖"，
  而绽裂的入场券是"超容量"（`RitualEffects.java:287`）。
  一个玩家可以用余烬砖**精确地把杖灌到刚好超容量**，从而**跳过 30 秒仪式**。
  但这在《倍率总表与意见》§9.6 里本来就被点名为"超容量 1 点门槛太宽松"的问题，
  余烬砖只是让它更省事 —— **建议与 #8（把门槛改成 `amount ≥ capacity × 1.5`）一起做**。
- **会不会破坏"另一半彻底消失"的设定？** 会。
  作者在第二阶段方案 §11 Q6 明确写"彻底消失"。
  **但请注意**：那条设定是针对**通用规则**下的，而这里给的是**一种特定材质的特例**——
  与"灵魂允许混装""紫珀砖共享"是同一层级的"材质例外"
  （《实现设计》§13.3 "材质级的例外"那张表）。**建议以"加入那张表"的形式落地，而不是改通用规则。**
- **存档负担**：余烬砖是物品，跟着物品走，**不需要新存档格式**，风险低。

### 实现难度

**中**：新物品 + 新组件 + 方块实体加一个待产出字段（并顺手修 `ritualPayload` 的序列化）+ 一处右键交互。

## 方案 B　炙烤：下界砖的沉坠"不挑食"

**建议 trait 名**：`NETHER_BRICK_GREED`

### 效果

下界砖作为**中心**时，**沉坠仪式取的是整条记录的全额，而不是负面那一份**。
即 `share` 从 `(1 - ratio)` 改成 `1.0`，但注入量额外 `×0.55` 作为代价。

### 它创造了什么玩法

它把下界砖变成**"参半记录处理机"**：
`ratio = 0.5` 的记录，别人沉坠只能拿一半（16 点），下界砖能拿全部（32 × 0.55 ≈ 18 点）。
**对那些"随手记的普通记录"（占了玩家记录的大多数）更划算。**
玩法变化很小 —— 只是在配装时多一个"我手上参半记录多，那用下界砖"的判断。

### 实现落点

`RitualEffects.inject()` 的 `double share = positive ? st.ratio() : (1.0 - st.ratio());`
（`RitualEffects.java:138`）之后加分支。

### 平衡风险

**中**。这是**纯数值**特性，而纯数值特性的风险正是"让某一种类成为无脑最优"。
算一下：`ratio = 0.5` 时 18 点 vs 普通中心 16 点（+12 %）；
但 `ratio = 0.2`（负面重的记录）时，普通中心拿 0.8 × 32 = 25.6 点，
下界砖只拿 32 × 0.55 = 17.6 点（**-31 %**）。
所以它是**有得有失**的，不是支配 —— 这一点比方案 C 好。

### 实现难度

**小**（一行算术）。**但玩法价值也最小** —— 它不会让玩家做任何新的事，
只会让玩家在**已有的选择里换一个选项**。**不推荐作为独占特性**，
但可以作为方案 A 的**附加小菜**。

## 方案 C　灼热执着：下界砖"不削弱负面"的升级版

**建议 trait 名**：`NETHER_BRICK_ZEAL`

### 效果

下界砖作为中心时，**负面注入额外 ×1.20**，
并且**沉坠仪式的失败分支被取消** —— 即 `total ≤ 0` 时（`RitualEffects.java:148`）
不消耗记录、也**不**报"情绪太平淡了"，而是照常以 `max(1, ...)` 注入 1 点。

### 它创造了什么玩法

几乎不创造。它只是把"下界砖当负面中心"这条路变得更稳。

### 实现落点

`RitualEffects.java:148-166` 的失败分支加条件跳过 + `:184` 的 `pref` 乘一层。

### 平衡风险

**高，且方向不对**。
① 它**加大**了《倍率总表与意见》§9.1 已经点名的"沉坠天生弱 15 %"的不对称
（因为沉坠的第 1 名是紫珀砖/末地岩石，第 4 名才是下界砖；
给第 4 名加强只会让中间档更挤，不解决头部断层）。
② 取消失败分支会让 `RitualEffects.java:148-166` 那条**花了一条记录换 0 收益**的
"痛苦但诚实"的反馈消失，而这恰是该系统少见的**清晰失败信号**。

### 实现难度

**小**。**但不推荐** —— 它属于"加了数值、没加玩法"，
而作者这次明确说了"优先追求点子本身的玩法价值，而不是数值强弱"。

## 3.4 三个方案的横向对比

| | 方案 A 砖窑 | 方案 B 炙烤 | 方案 C 灼热执着 |
|---|---|---|---|
| 做什么 | 把废弃的那一半变成**可搬运物品** | 改"取哪一份"的算法 | 加乘数 + 取消失败 |
| 玩家会改变的行为 | **会把下界砖摆进仪式场、会攒/带/交易余烬砖、会重新看待参半记录** | 配装时多一次判断 | 无 |
| 新增内容 | 1 个物品 + 1 个数据组件 | 0 | 0 |
| 是否新玩法 | ✅ 是 | ❌ 否（只是新的最优解） | ❌ 否 |

| 难度 | 中 | 小 | 小 |

## 3.5 推荐：**方案 A（砖窑）**

**推荐理由（四条，按重要性排序）**

1. **它是三者里唯一"让玩家多做一件事"的方案。**
   方案 B/C 都只是让下界砖在**已有的决策里更好一点**，
   而《实现设计》§13.3 的整张"材质级例外"表（灵魂混装、紫颂花随机、紫珀砖共享）
   **全部都是"增加一种新行为"，不是"增加一个乘数"**。
   方案 A 与这张表同源，B/C 不是。
2. **它复用了现成的最复杂那部分。**
   "被抛弃的那一半"这个数据在 `RitualEffects.java:139` 已经算出来了（`share` 与 `amount`），
   而现在它是**直接扔掉**的。方案 A 是**把已有的废弃物利用起来**，
   不是往系统里塞一个新概念 —— 这是最低摩擦的加法。
3. **它顺手修掉两条既有隐患。**
   做 A 必须碰 `EmotionStatueBlockEntity` 的"仪式结束时产出"这段，
   而这段现在**没有序列化 `ritualPayload`**（`:549-557`），
   意味着**升华/沉坠中途退出游戏会丢注入**。一次改动顺手修掉。
4. **它对"下界砖最平"这个诊断是直击的。**
   下界砖的定位是"下界的砖"——**砖是建筑材料、是砌起来的东西**。
   "把情绪砌成一块砖"是这个材质**语义上最自然**的能力，
   比"负面 +20 %"（方案 C）或"多取一份"（方案 B）更贴合它是什么。

**落地建议的顺序**：先做方案 A 的**最小可用版**（只在 `finishOuterRitual` 生成一块砖 +
右键灌入），把"砖的极性/属性/点数"这三个字段定下来；
把它接进指南书（`GuideBookPages` / `ModBookContent`）作为下界砖条目的说明，
**这一步做完就算完整**，不需要一次做全套。

# 第四节　我的取舍建议

## 如果只能做 3 个

**做这 3 个，按这个顺序**：

### 第 1 个：**点子 1　回响（`ECHO`）** —— 先做，因为最便宜且立刻可感知

- **为什么**：它是全清单里**唯一的小工程 + 无新状态 + 无新包 + 无存档改动**的一条，
  却直接改变玩家最常做的那件事（挥杖）。现在 `EmotionStaffItem` 的三种用法
  （`EmotionStaffItem.java:84-101`）**只有一种形态**（半径），
  加五种形态属于"在已有的一个方法里做分派"。
- **为什么排第一**：它**零风险**（不碰数值、不碰乘数、不碰存储），
  可以作为"证明这套特质机制能接线"的第一个样板 ——
  而这恰好回应了你最担心的那件事（"不想再往一套没接线的机制上加东西"）。
  它做完之后，`StatueTrait` 里就会**第一次**出现"能改变行为的布尔方法"，
  后面几个点子的落点也就有了示范。

### 第 2 个：**第三节 方案 A　砖窑** —— 紧接着做，因为它是你点名要的，且顺手修隐患

- **为什么**：作者点名要下界砖的功能，且这条顺带修掉
  `EmotionStatueBlockEntity` 不序列化 `ritualPayload` 的既有丢失问题。
- **为什么排第二**：它需要新增物品 + 数据组件（有学习成本），
  但**不依赖任何其它点子**，可以独立完成。
- **注意**：与它一起做《倍率总表与意见》#8（绽裂门槛 `amount ≥ capacity × 1.5`），
  否则余烬砖会让"超容量 1 点"这个本来就没意义的口子更没意义。

### 第 3 个：**点子 7　补料（`SUBSTITUTE`）** —— 最后做，因为它解决的是最痛的那道墙

- **为什么**：这条的收益**不在"强"而在"通"**。
  现在凑齐"四尊同类外围"是真门槛（`RitualStructure.java:185-188` 明确拒绝混类），
  而仪式是整条链的**唯一入口** —— 门槛卡住的不是收益，是**能不能玩到**。
  让结构判定从硬墙变成可议价的成本，是这三条里对**留存**影响最大的。
- **为什么排第三**：它要改 `RitualStructure.Result` 的结构，
  牵连 `match()` 的三个分支与 `MadnessCommands` 的调试输出，改动面比前两条宽。

## 如果你愿意做第 4 个

做 **点子 11　交换台（`BARTER`）**。
理由：它是**唯一一条能拆掉"记录顺序死锁"**的方案 ——
而那个死锁是代码注释里**明确记录过**的设计教训
（`StatueTrait.java:24-27`：删除「仅容纳」硬门槛的**唯一理由**就是它）。
现在这个教训只是被"绕开"了（改成 ×2.00 奖励），**并没有被解决**。

## 关于"先把空功能接上"这件事

最后提醒一句，**顺序上应该先于所有新点子**：

`allowsMixing()` / `randomFluctuation()` / `sharedStorage()` 这三条现在会**出现在玩家的
F3+H tooltip 里**（`EmotionStatueItem.java:77-79`）和**调试指令的输出里**
（`MadnessCommands.java:246-248`）。也就是说：**玩家现在能看见三个不存在的功能。**
这是一个**正在对玩家撒谎的 UI**，比"空功能"本身更值得优先处理。

三条路，任选其一，**都很便宜**：
- **接上**：`randomFluctuation()` 接进 `RitualEffects.java:338`（把 `0.8 + rng*0.4` 换成
  trait 有特性时 `0.6 + rng*0.8`，其它材质不变 —— 一行）；
  `allowsMixing()` 需要先定义"混装"是什么（中）；
  `sharedStorage()` 见点子 6（大）。
- **或摘掉**：把 tooltip 与调试指令里那三行删掉，注释标"未实现，见《雕像特殊功能点子.md》"。
- **至少**：在 tooltip 那三行后面加"（未实现）"，别让玩家以为是自己没触发。
